# WEXPC：GPT × GitHub 工程协作规范

状态：正式生效（2026-10-27）。本文件只管理开发工程 D 域，不改变 WEXPC 产品基线、0.1.1 功能范围、产品内 M 域多 Agent/Dispatcher 权限模型。

## 1. 权威入口和开工核对

- 产品范围以 `docs/PC-PRODUCT-AND-TECH-BASELINE.md` 为准，施工链路以 `docs/WEXPC-0.1.1-IMPLEMENTATION-PLAN.md` 为准；工程执行以本文件及 `AGENTS.md` 为准。
- 每批开始直接查询 GitHub 最新 `main` HEAD、开放 PR、现存远端分支、近期 Actions、相关源码及原有测试；不要沿用历史摘要中的旧 SHA 和旧分支数量，也不要求用户中转日志、Run ID。
- GPT 按已批准的目标主动完成可验证的连续工作，必要时进行技术反对、审查与纠错；产品边界、权限扩大、发布决策等必须尊重用户授权。不同施工者同时修改时，先核对文件范围和 HEAD，采用串行接线或必要的短期隔离。
- Issue、PR、Tag、Actions 是工程协作设施，不代替产品内 Task、Operation、Receipt、Review 或 Context。

## 2. main 优先：七项已确认规则

1. **默认在 main 施工。** 一次选择完整功能链路，拆成小批提交；提交前检查 HEAD、文件和影响范围，失败先定位修复并增量复测，不为普通修改开分支。直接 main 提交须尽可能保证每次提交可构建、可回退，未完成特性可保持不启用。
2. **短期分支只用于必要隔离。** 并行修改冲突、高风险数据变更、未批准的架构实验，或确需独立审查时使用；明确目的、负责范围、起点 SHA、结束条件。完成后先确认成果和验证，再整合/归档、删除；不长期积压。独立实验不能未经用户确认自动提升为正式产品设计。
3. **Issue 记录持续事项。** 重要 Bug、跨批次工作、决策阻塞、需追踪的验收缺口建 Issue；日常小修不强制新建。关闭 Issue 不意味着代码已测试或交付。
4. **PR 服务于审查。** 高风险和并行开发才默认使用，PR 显示 Diff、审查和测试证据；完成后及时整合并关闭，核对远端分支确实删除。单纯关闭 PR 不代表 merged，也不代表分支删除。
5. **每批报告真实证据。** 必须包含目标和范围、起点/交付 Commit SHA、改动文件或接口、实际执行的命令/环境/结果、Actions Run/Job（如果使用）、NOT_RUN 项目及原因、未完成事项。提交成功不是测试通过；CI 通过不是 Windows 实机验收。
6. **归档不等于合并。** 历史分支被删除或归档标签存在，不等于其独有代码已经进入 main。必须按源码、测试、权限与接口差异分类：已覆盖、需要回收、明确废弃、待决定；必要成果经过审查与验证后小批次整合主线。归档 Tag 需保留至回收核查结束。
7. **正式交付才创建 Release。** 开发 Commit、Git Tag、Actions 成功、Windows 构建和真实 Windows 安装/交互验收是不同证据；只有达到既定交付条件才创建对应正式 Release，不伪称已交付。

## 4. GitHub 功能的最低成本使用方式

- Repository / main：源码、权威文档及可追溯提交的唯一日常集成主线。
- Issue：只跟踪跨批次且需持续追责、复验或用户决策的事项；避免为每个机械修复建立 Issue。
- Branch / PR：用于隔离和评审而非默认三件套；不设常驻 `develop`、`integration`、`release` 分支。
- Actions：按影响范围选择 Linux/Rust、前端、Windows 或集中全量；不为每个 Commit/归档分支重复跑全部平台。
- Tags / Releases：历史归档 Tag、里程碑 Tag 与公开交付 Release 语义分开；Tag 是恢复入口，不证明正式采用。
- 安全：普通测试最小只读权限，写入工作流单独审批并限定用途；不得提交密钥、私有资料或未审查产物。仓库公开状态不代表任何资料都可公开。主线不强推、不随意删除。

## 5. Actions 的查询、触发与失败修复

- GitHub 通用读取接口：`https://api.github.com/repos/owla19s-ux/wexpc/actions/runs`；根据最新相关 run 的 `head_sha`、状态、结论查询 Job、Step 和失败日志，不要求用户提供 Run ID。
- 当前工作流支持受限请求文件触发：`.github/ci-requests/linux/**`、`.github/ci-requests/frontend/**`、`.github/ci-requests/windows/**`，以及 `workflow_dispatch`。触发前核对工作流当前定义及目标 SHA；避免重复、循环、无关运行。
- 每批先做定向验证，稳定集成节点再做必要的 workspace/前端/Windows 回归；Windows CI 与桌面安装、凭证与交互实测分开。失败先读取日志、修复，再核对新 SHA。
- 旧文件 `docs/DEVELOPMENT-WORKFLOW.md` 中的 2026-10-24～31 Actions 暂停、双施工者固定分工、已删除的 PR/分支起点属于**历史快照**，与本文冲突时以本文现行规则为准；其技术验证命令及安全/平台限制仍可参考，但必须基于现有仓库重新验证。
