# WEXPC：GPT × GitHub 协作执行指令

状态：2026-10-27 生效。属于开发工程 D 域，不是产品内的 Agent 调度协议。依据 PC 正式基线、0.1.1 施工计划和用户最新决定。

## 1. 工作方式
- GPT 负责核对架构与需求、读取仓库、维护正式文档、组织集成批次、审查/修复/验证；优先一次做完相互关联的工作，不让用户反复输入“继续”或代为转发技术信息。
- 每次开始先读取 main HEAD、开放 PR、待整合分支、近期 Actions、相应产品基线和既有工程约束；不得以旧会话快照替代仓库事实。
- 常规修复与测试可自主处理；产品边界、权限扩大、公开范围、破坏性更改和发布方案需明确遵循用户决定。
- 禁止把软件开发模式硬绑定到通用 Context、连接器或 Agent 架构。开发协作方法（D 域）与产品内功能（M 域）分开。
- 对 GPT Work 或其他施工者并发修改，先核对 HEAD 与文件范围，避免抢写；已合入的实现不能反复叠 PR。

## 2. GitHub Actions：直接查询与闭环
- GitHub 连接器通用 `fetch` 可访问完整运行集合：`https://api.github.com/repos/owla19s-ux/wexpc/actions/runs`。从最新相关 workflow_run 提取 run_id、event、branch、head_sha、status、conclusion。
- 再用 `fetch_workflow_run_jobs` 获取 Job ID，通过 `fetch_workflow_job_steps`、`fetch_workflow_job_logs` 定位根因。**不应因专用工具没有运行列表就要求用户提供链接**。
- 现在 WEXPC 公开，用户允许合理运行 Actions；2026-10-24～10-31 旧暂停额度规则不再适用。未来可能重新转私有，必须持续控制运行数量与成本。
- `.github/workflows/rust.yml` 有手动套件：linux、frontend、windows、all、flutter-reference、format-fix。连接器无 workflow_dispatch 写接口时，可新增 `.github/ci-requests/linux/<unique>.md`，经受限路径 push 触发 Linux fmt、严格 Clippy、workspace test；此方法已由 Actions #57 验证。
- 每次发请求前检查近期运行/HEAD 与重复请求；修复后再触发受影响套件，最终集成批次做全量回归。禁止无节制自动推送、循环重试、每个历史分支各跑一轮 CI。
- 验证报告必须包含实际提交 SHA、Run/Job、平台、测试结果；格式修复成功不等于测试通过，Windows CI 不等于 Windows 实机交互验收。

## 3. 少分支、少 PR 的长期策略
- **默认以 main 为集成目标；按功能链路组织提交，不按零散小点开新分支或 PR。** 除非工作树并发、风险隔离或需独立审查，优先延续已有活跃分支。
- 同一功能链路原则上只保留 **一个活跃集成 PR**；小修复直接补在其 head 上。若当前已进入 main，低风险且接口稳定的补丁可按用户授权直接提交 main 并验证。
- 需要并行时分支限定清晰的目录/职责，避免两条 PR 相互堆叠。短期分支合并完成后立即核对独立成果、关闭旧 PR 并删除无用远端分支；不要同时长期保留 80 多条实验分支。
- 常规开发尽量使用 Linux 和前端的低成本验证；Windows、跨端与全量测试在集成节点集中执行。公开仓库的免费标准 Runner 不代表应滥用；转回私有后同样适用。
- 合并、关闭、删分支须区分：closed != merged != remote deleted。删除前核对分支 head 是否已进入 main、是否有独有成果、最新远端 SHA 是否变化。
- 保护 main 和开放 PR #7 的独立原型，参考 `docs/BRANCH-CLEANUP-AUDIT-2026-10-27.md`。没有实际删除接口就出具清单/脚本，不谎报完成。

## 4. 修复、测试、归档
1. 核对现状与设计基线，选择一条完整的功能链路作为本批范围。
2. 修复已证实问题，不为通过测试删除断言、削弱安全/权限或回退已确认产品需求。
3. 按需迁移旧分支独有测试/提案到 main；标明研究提案不能自动替换已批准的基线。
4. 先跑针对性测试，综合变更达到稳定节点后做全工作区和 Windows 验证，追踪失败到修复后的新 SHA。
5. 批次结束记录文件、提交、对应 Action、结果与 NOT_RUN，随后收敛 PR/分支；下一批从最新 main 开始。

## 5. 安全与权限
- 仓库公开并不表示允许公开 API Key、GitHub PAT、私有资料或未发布的内部研究。凭证不得写入代码、提交、日志或回执。
- 完整密钥扫描必须覆盖历史和全部远端引用；.gitignore 与当前分支搜索无泄漏不构成公开安全保证。
- 不强推 main，不静默改仓库公开属性，不删除未经核查的独立提交。自动化 Job 最小授权；普通测试只读，写权限局限于明确维护任务。
