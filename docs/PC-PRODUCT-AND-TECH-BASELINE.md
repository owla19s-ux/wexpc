# WEX PC 产品、功能与技术基线

- 状态：WEXPC 当前产品与技术**工作基线（已进入 main，尚未整体冻结）**。PC 优先及 0.1.1 的轻项目管理、Agent/多 Agent 施工与本地工具能力已确认；新增阶段划分、具体选型及尚未收敛的交互细节仍分别标注待验证或待确认，不因写入本文自动获批。
- 适用仓库：WEXPC。
- 本文不代表所列功能已经实现，也不代表 Windows 实机验收通过。
- Android 文档和代码仅作为已确认业务语义、架构、安全原则及可复用模块的参考；PC 的 UI 技术与交付顺序由本基线决定。

面向协作者的直白解释与实例见[项目共识说明](PROJECT-CONSENSUS.md)，工程分批与当前缺口见[0.1.1 施工路线与链路验收计划](WEXPC-0.1.1-IMPLEMENTATION-PLAN.md)。版本/需求仍以本文为准；施工计划不是另一套功能基线。

## 1. 产品方向

WEX 当前优先建设 PC 产品，首期目标 Windows。产品长期以统一工作对象和自由画布为重要交互方向，软件开发是第一个落地的工作模式；自由画布与多视图接线不作为 0.1.1 首版完成条件。聊天记录不是唯一事实源；对象、关系、执行状态和验证证据应独立保存。

此次变更是 WEX **整体开发重心由 Android 转至 Windows PC**，不是把 Android 0.1.1 的精简版搬上 PC，也不是创建业务语义不相容的新产品。Android 0.1.1 中因阶段成本而后置的产品能力必须重新纳入 PC 完整范围审视，但原来只是讨论、候选或后续研究的内容不会因此自动成为已确认的首批交付要求。

PC 不等于把 Android 页面放大。Android 可提供连接器、安全边界、权限/撤权、操作生命周期、失败恢复、GitHub 回读核验等参考，但 Android 页面结构、Flutter 工程形态和旧版本顺序不约束 PC。

## 2. PC 产品功能范围（不等于全部在首个批次交付）

### 2.1 工作对象与画布

2026-10-24 当前施工重点：先根据架构整理仓库职责并建设核心/基础服务，优先 Space、Context 与轻项目管理。0.1.1 先提供基础的空间、可选分组、通用上下文、项目关联与持久恢复；UI 细节后续细化。该顺序不取消已确认的本地开发、多 Agent 并发、独立验证/审查与模拟器目标。

本节描述 PC 产品完整方向。0.1.1 先提供可操作的轻项目管理、对话、任务分派、多个 Agent 施工状态及证据界面；自由画布和多视图接线可在后续批次或版本完成，后置不等于删除对象与关系的扩展需求。
- 对象使用稳定 ID；对象内容、层级、依赖/一般关系、画布布局分别建模。
- 支持树形与网状关系，不能将整个数据模型限制为单一树。
- 自由画布支持创建、选择、编辑、移动、连接、分组、缩放和平移。
- 画布、表格、列表、树形、看板和详情视图读取同一权威数据。
- 支持自动保存、撤销/重做、历史恢复和数据导出；具体事务与历史契约在实现前定义。
- 无 AI 连接时仍能手动组织本地工作数据。

### 2.2 AI 秘书与模型
- 管理多个 API 连接、服务商和模型；优先验证 DeepSeek 与 OpenAI 兼容 API。
- 秘书模型与专业执行模型可分别配置；不将 AI 角色固定为不可扩展的名单。
- 对话可引用工作对象、画布区域、项目和任务，但不取代正式业务状态。
- AI 对结构、文本或代码提出变更时，支持预览、调整、接受和拒绝。
- 清晰区分用户已确认内容、AI 建议、待确认、排队、执行中、成功/失败、结果未知与独立验证通过。
- 执行策略统一为自动执行、询问后执行、拦截；凭证权限、OS 授权和操作安全检查仍独立生效。
- 支持编辑消息后重新生成、生成期间追加消息排队；不得把重发消息误当作撤销已发生的外部操作。

### 2.3 API、连接器与权限
- 连接、服务商、模型、会话身份和工具能力分开建模。
- 凭证与普通配置分离；密钥不得进入日志、对话内容或普通业务数据库。
- 连接器统一声明能力、输入输出、授权要求、超时、取消、错误与结果未知语义。
- 连接测试、模拟响应、真实服务商响应必须明确区分。
- 用户可以查看、撤销和限制连接权限；撤权不能只改 UI 标记而不影响后续请求。

### 2.4 本地软件开发链路（WEXPC 0.1.1 明确需求）
- WEXPC 0.1.1 必须让用户配置 AI API 后，在 Windows 本机选定项目及相应授权范围，由 AI Agent 通过 WEX 的受控工具调用操作本地文件与代码环境，完成基础的读取、修改、运行、测试和编译，并根据真实工具反馈继续处理或向用户报告。普通对话与软件开发工作模式均能使用适用的本地工具能力；软件开发模式负责持续任务组织，不能成为每次普通工具调用的前置。
- 编译器、解释器、语言 SDK、构建工具与项目依赖可以使用用户本机安装或外置的现成环境。WEX 提供环境发现/选择、调用、进程管理和结果接线，不要求自行打包所有语言的完整工具链；具体环境支持范围与安装指引按实际适配记录，不把单一语言或单一项目样例当产品上限。
- 用户明确选择项目目录后，在授权范围内读取和修改文件。
- Windows 本地环境纳入 Android SDK 与模拟器：选择/启动设备、安装运行构建、执行适用测试并读取日志，失败进入同一修复链；模拟器验收与真机验收分别记录。
- 集成本地 Git 状态、差异、分支、提交、冲突与回读。
- 支持从 AI 工具调用或用户界面启动项目已有的运行、构建、测试和打包命令；记录实际命令、工作目录、所用环境、进程状态、退出码、日志摘要、产物位置和时间。进程完成或失败的结果回到 Agent 上下文与用户可见界面，便于继续修复或复核。
- 软件开发模式需要较完整的本地 Agent 能力：在用户明确授予的项目/工作目录及可用代码环境内，可连续调用文件操作、终端进程、本地 Git 与适用连接器，运行项目所需的多步骤命令并读取结果；不把每条命令、每个文件或每次工具调用都变成逐项重新授权。用户可查看、调整和撤销授权，执行策略可设为自动执行、询问后执行或拦截；对授权外范围和新权限需求应提示用户决策。
- 本地进程具备可见状态、超时、取消、失败报告和审计记录。命令能力的范围按用户授权与执行策略决定，不能由单一演示项目固化成永久的命令白名单；也不因较宽能力推定默认全盘访问。
- 区分外部请求已接受、已派发、结果已知/未知、结果已持久化和独立核验通过。
- 验证时先在 Windows 本地打通一条真实项目闭环：选择项目与代码环境 → Agent 读取/修改 → 运行或测试/编译 → 获得真实结果 → 依据反馈继续或报告。验收要同时覆盖命令失败、环境缺失、用户取消、超时、权限撤销和重新进入项目后的状态。远程开发、容器、云端 CI 属后续连接器，不作为这条本地闭环的替代。

DSH 参考的是“模型 API → Agent 工具调用 → 本地文件/终端执行 → 输出和退出状态返回模型”的实际机制（参见 [DeepSeek Harness 官方使用指南](https://deepseek-harness.github.io/deepseek-harness/en/guide/quickstart)与[官方 Shell 文档](https://deepseek-harness.github.io/deepseek-harness/en/reference/subsystems/shell)）。这只是能力和交互参考，不表示 WEXPC 已采用 DSH 的代码、插件架构或权限默认值；WEXPC 的运行环境、授权和回执仍按本基线独立设计。

### 2.5 GitHub 与验证
- 首版实现真实 GitHub 连接、仓库读取、受控修改、提交、回读和内容核验。
- 遵循正式授权范围；不能以 AI 生成的建议替代用户授权。
- 不得把 GitHub 的验收结果外推到其他托管平台。
- 外部写入结果未知时，不得盲目自动重试可能产生重复副作用的操作。

### 2.6 语音
- 鼠标与语音是目标主要交互方式，键盘和快捷键作为补充。
- 语音指令结合当前选中对象和已确认上下文；关键范围不明确时请求澄清。
- PC 产品方向包括基础语音输入；其 0.1.1 验收深度待确认。识别引擎、TTS 和角色表现另行评估，不作为本地软件开发闭环的前置。

## 2.7 2026-10-25 PC 迁移补充：调度、职责权限与细粒度对话

本节将此前已确认、但在 Android→PC 迁移或最小桌面原型中容易被弱化的行为明确纳入 WEXPC 产品范围。优先级：**已确认的 PC 0.1.1 本地持续施工与多 Agent 能力不变；尚未确定版本的完整交互、跨设备与生态能力仅保留设计，不因本节自动升格为 0.1.1 交付要求**。具体实现接口和数据表尚未冻结，任何「已规划」不等于「已实现/通过验收」。

### 2.7.1 通用 Dispatcher 不是主 AI，也不是单纯的任务状态机

- WEX 通用底座保留 **Connection / Connector、Dispatcher、Permission / Approval、State / Evidence、Host / Tool Runtime** 各自边界。Dispatcher 是**程序化调度机制**，不能借此让某个模型垄断 Core；普通对话或其他连接操作不强制先创建 Task。
- Dispatcher 应组织能力选择与路由、投递/接收、排队和并发协调、任务及操作生命周期、事件/回执索引、审查/验证交接、外部状态刷新、异常升级、持久恢复。具体常驻形式（进程/服务/宿主内部组件）、调度算法、自动唤醒条件和队列协议**待工程设计/验证**，不能由「应是程序」擅自推出必须是独立 OS 进程。
- Agent 的**认知判断**与 Dispatcher 的**确定性流转**分离：主 AI 负责理解目标、规划、发布/调整任务；施工者负责实际修改；审查者形成审查结论和同范围修复要求；Dispatcher 在有效规则下转送并记录，不自行产生技术修复方案、改变正式需求或扩大权限。
- 工具执行成功 ≠ 测试/审查通过 ≠ 任务完成 ≠ Windows 实机验收；任何模型的自述都不能替代真实外部事实。未知结果不自动重试有副作用的操作。
- 允许独立 API 驱动 Agent 与符合适配契约的外部 Agent 运行时；Agent 身份、职责、Provider/Model、会话、运行时、Connection 与权限必须分离。特定第三方运行时是候选，不构成默认内置或 0.1.1 必装依赖。

### 2.7.2 职责权限分级与持续授权

- **职责范围不是一个从低到高的超级管理员等级**。角色模板表达工作责任及默认允许的受控业务动作；实际决策另看 OS 权限、Connection 启用、Context/项目/资源授权、Agent/会话/任务范围、能力动作及执行策略。项目/Space 关联和模型相同都不能产生授权继承。
- 项目主 AI：可按适用授权阅读项目基准、计划、状态、任务与证据，提出/维护施工规划与状态快照；已确认重大需求/架构变更需用户确认，不自动拥有全盘文件和任意命令权限。
- 施工 AI：以已发布工作范围为限读取必要资源、提出和按授权执行修改、构建、测试及提交，报告事实；不可更改原始 Dispatcher 事件、其他任务、审查记录或自行宣布最终验收。
- 审查 AI：在**同一项目有效只读授权范围内**可较广泛阅读规范、代码、Diff、版本和证据；通过受控接口追加审查结论、同卡修复建议或升级请求，通常不直接写项目正式代码/架构/任务卡；可按另行适用授权发起验证。
- 验证职责：对具体版本及环境执行或核对实际构建、测试与运行证据，不以「模型判断通过」替代工具结果；验证职责的独立模型、分工和更细权限仍待细化。
- 用户级秘书：按明确授予的跨 Context 范围汇总、提醒和交互；不是所有项目的默认超级管理员。Dispatcher 不是 AI 权限主体，不应从任务分配导出额外资源权限。
- 支持可检查、可调整及可撤销的授权，执行策略至少区分**自动执行 / 询问后执行 / 拦截**；批准范围内连续操作不应永久退化为「每读一个文件、每次编译都重新批准」，但范围外、高风险或需新增决策的行为仍受适用审批。具体授权期限、委托、撤权竞态及高风险动作规则待设计与验收。
- 一个模型可分别担任多项职责，不同 Agent/任务/会话不因此共用相同身份或读写权。职责权限、资源授权和执行策略分别可审计。

### 2.7.3 对话序列号、逐段确认与引用回复

- AI 回复可以按稳定的**有序序列项**（例如 1/2/3）呈现，每项支持独立选中/引用、确认勾选、拒绝/不采纳（叉号）、局部补充或修改以及独立讨论分支；一轮可选多项组合回复。**段落勾选与任务卡选择是两种不同语义**，不能将确认勾选当作工具写入审批、实际执行或 Verify 通过。
- PC 常用的勾/叉入口按原方案默认可见，补充输入与分支入口可按鼠标悬停出现；细项可展开子项清单逐项处理。各项的状态、来源、历史版本和与主线关系应可恢复，分支结论不可静默覆盖既有已确认内容。
- 用户可以按序号以文字/语音指向具体条目（如「第 2 项不采纳、第 3 项讨论」），歧义时确认。序列交互和分支功能可按需配置开关并提供引导，不把隐藏图标等同于禁止底层交互。
- **编辑已发送消息后重发**与**生成中追加排队发送**独立：后者不隐式停止当前模型回复，当前工具副作用不会因编辑/追加自动撤销；排队、撤回、重发的历史与防重复操作规则待定。
- 序列项应有可引用、持久的对象身份及权威状态，不得只根据一段渲染文本临时编号并以此冒充稳定 ID。Message、Sequence Item、Selection、Reply、Branch 与用户决定在概念上区分；**不在此冻结数据库表、消息协议或 UI 组件**。
- **范围状态**：上述交互为原 PC 设计中已经记录的跨端产品方向；其完整 UI 在 0.1.1 的交付归属**尚未确认**，但必须纳入 WEXPC 产品与数据演进审查，不能因为暂缓画布而抹除。原始行为见 WEX `docs/UI/PC/README.md` §2.5。

### 2.7.4 PC 本地多 Agent 施工与执行环境

- 0.1.1 已确认：多个独立 Agent 能在**互不冲突的任务与授权范围**内并行施工，真实读写多文件、使用本地编译/运行/测试工具与本地 Git/GitHub，获得可核验结果并持续交接。不是只允许并行聊天，也不能只用单 Agent 演示冒充多 Agent 施工。
- 按实际资源/文件及写入范围协调占用，隔离或协调工作树、构建输出和进程，识别重叠写入与版本变化；冲突时暂停/阻止或上报，不能让两个 Agent 静默互相覆盖。资源占用粒度、隔离机制与调度并发上限**尚未冻结**。
- 开发环境是可发现/配置/选择的能力来源，本机安装的 Cargo、Node、Python、Flutter、Android SDK/ADB/模拟器及其他项目所需工具不可被单一 Cargo 演示白名单定义为产品上限；真实执行仍须 OS 与 WEX 授权、超时取消、进程/退出码/产物/日志、结果未知与回读核验。外部 Agent 和远程/容器/CI 依对应阶段另行适配。
- 项目基准、Task/卡版本、成员职责分配、Agent 会话、执行尝试、Dispatcher 事件、Review/Verify、外部 Commit/Run 与待用户决定事项应能持久关联；聊天不是权威项目状态。重启恢复先核对真实状态，不重新执行不明副作用。
- Windows 0.1.1 的**已授权范围内持续施工**不要求用户每几分钟重新发一次「继续」；不能据此解释为应用/PC 已关闭仍必须运行，也不能允许未经确认的新范围。

### 2.7.5 后续完整 PC 设计不得因 Android 旧缩减而删除

- 自由画布和多视图共享同一工作对象；支持鼠标直接定位段落/节点/关系，后续语音与秘书根据当前选中对象协作。PC 操作区域可按惯用手镜像。画布及多视图的具体版本仍待确认，0.1.1 不以完整画布为门槛。
- 项目主 AI 与用户级秘书分离；秘书可按有效范围跨项目汇报/通知，未来角色状态、TTS、动作和情绪表现不等于现阶段已接入。
- PC/手机不仅同步进度，也保留**手机遥控 PC 实际工具执行**的产品方向；设备关联≠文件/终端授权，执行位置、指令收取、结果核验与状态同步要分别记录。全屏静默及是否转发手机由用户配置。
- 小说等不同工作模式、公共结构化知识与方法库、账号/云服务、外部连接和跨端能力仍是完整产品范围的规划或候选，不能拿 Android 的阶段删减当 PC 永久产品边界；未确认版本不作 0.1.1 承诺。

### 2.7.6 本次纳入仅为需求回收，不是代码验收

截至本节整理时，WEXPC 开发分支的项目、Agent 和任务记录/工具入口已具备部分代码，但**不等于** Dispatcher 常驻调度、多 Agent 并发安全写入、持久职责 ACL、持续授权或序列分支聊天已经正式接通。应在后续独立施工批次提供可核实的实现、测试与 Windows 验收证据，再逐项调整状态。本节保留原 PC 文档与 WEX 协作架构原文的追溯关系。

### 2.7.7 后续 PC 悬浮入口：角色形象 + 可展开面板（规划，不施工）

- WEXPC 保留 **AI+ / 维加早期的悬浮入口、动态上下文面板**这一交互方向；参考 Nanomuse 的虚拟角色形象与交互面板组合，但不是照搬其代码、默认授权或固定视觉效果。角色形象可用于显示状态、进入对话和展开面板；面板可展示当前项目/对象、对话、待确认序列、任务状态、通知及适用工具入口。它是同一 WEX 状态与能力系统的另一种**交互呈现**，不是第二套秘书、数据库、权限系统或独立调度器。
- 早期 AI+ 的设计重点是 `+`、`@`、输入/对话及任务卡可跨页面贯通；维加的浮动入口强调依据当前对象与可用能力动态呈现，而非固定的单功能聊天按钮。WEXPC 取其**与当前项目/文件/窗口选中对象相联系**的交互原则；从某处唤出面板，应在受支持的范围内延续当前工作上下文，而不是让用户反复解释对象。未获用户授权的屏幕、文件、其他应用内容不得自动被读取。
- 悬浮面板应可展开、收起、移动与配置；可进一步研究非打扰呈现、确认/重要异常时轻提示、执行时后台静默，以及虚拟形象的表情、动作、TTS 与工作状态关联。Windows 悬浮层的置顶行为、窗口焦点、全屏游戏/影片、快捷键、语音、无障碍与多显示器兼容性需要专项验证。
- **明确后置**：本次仅纳入完整 PC 规划，暂不建设悬浮面板或角色动画，也不冻结 Nanomuse 风格、视觉尺寸、操作手势、实现框架及版本号；原 Android/BridgeFS 的尺寸、拖拽、吸边细节是历史实现/偏好，不能未经 PC 交互验证自动继承。

### 2.7.8 秘书 / 项目主 AI 的可兼任职责和长期记忆

- **秘书偏向角色形象、交互身份与岗位职责；项目主 AI 是某项目的工作责任。两者不是必然不同的 AI、模型或固定两个角色。** 同一个成员/模型/角色配置可以在适用授权下同时承担秘书与一个或多个项目的主 AI 职责，也可以分配给不同成员；同一主体在不同 Context 的具体授权、任务及可见资料各自独立。不得在代码中固定为两个必须同时存在的 Agent，亦不得因兼任而自动合并所有项目的读写权限。
- **记忆 ≠ 聊天历史 / prompt 常驻上下文。** 项目 AI 的长期认知应主要依托真实、可恢复的**项目文件和记录**：Project Baseline（目标、已确认需求和设计决策）、State Snapshot（阶段、进度、阻碍、待决定项）、Task/Card 与分派、工作日志、审查记录、测试/构建结果、实际文件版本与 Git Commit/PR/Run 引用。AI 可以按照受控写入规则追加观察、总结、交接及建议；重要基准不能因一轮回答被静默重写。
- 秘书还可能需要与具体项目无关的**角色与用户偏好/沟通约定**、跨项目待办/提醒以及经用户选择保留的长期互动记忆。这与项目主 AI 的项目知识、某次会话的短期上下文、工具凭证和独立执行日志是不同的存储及授权范围。秘书/主 AI 兼任时，可依当前职责**按需组合允许读取**的资料，但不把个人长期资料复制进所有项目，也不把项目机密写进通用角色记忆。
- 主体重新进入项目、换对话、换模型、切设备或程序重启后，应能从**已核验的基准与最新快照、真实文件/仓库状态和未完成事项**恢复必要上下文；使用按来源/版本/时间标注的索引或摘要控制 Token 成本，必要时回查原始文件与执行回执。摘要是检索加速物，不是唯一事实源。
- 记忆需要明确的**写入权限、来源/证据、时间与作用域、可信等级、冲突/过期处理、用户查看/纠正/删除、导出与恢复机制**。严格区分用户已确认事实、AI 推断、外部资料、待核实观察和过期结论。重复内容可去重整理，但不能悄悄删除关键决策历史；不能把模型猜测自动记为用户授权或正式架构。
- AI 使用文件作为记忆载体时，应保留用户实际可见、可编辑或可导出的项目材料与结构化索引之间的对应关系。文档是否由 AI 修改、涉及哪个版本和审批状态应可追溯；原始代码/项目文件由其实际来源保存，**不应为记忆系统无条件复制整个仓库**。备份、安全存储、敏感资料范围与跨设备同步仍需专门设计和用户选择。
- **版本边界**：0.1.1 已确定的项目基准、任务状态、操作证据、工作接续与重启恢复必须真实可用；完整用户级秘书长期偏好记忆、跨项目个性化、记忆检索/摘要策略、悬浮角色呈现及跨端同步为后续扩展或待确认深度，不因加入本节自动成为 0.1.1 全量交付门槛。

### 2.7.9 记忆与协作的待核实遗漏清单（设计约束，非自动批准新需求）

后续实施前需专项审查以下容易被遗漏的行为：**(1)** 同一主体兼任不同职责时的权限切换与审计；**(2)** 工作快照与真实 Git/File/Tool 状态不一致时的刷新与冲突呈现；**(3)** 用户已确认决策、AI 假设和外部不可信文本的来源区分；**(4)** 任务被重新分配、审查退回、不同 Agent 同时写入记忆时的版本保护；**(5)** 长时对话摘要丢失细节、错误记忆传播到其他项目或模型更换后的重新构建；**(6)** 敏感记忆删除、导出、备份恢复与跨设备选择性同步；**(7)** 悬浮面板涉及当前窗口/选中对象时的获取许可、焦点和静默策略；**(8)** 无 AI 网络连接时，项目与用户已保存的工作记录是否仍可读取和管理。

以上是应覆盖的失败场景与设计审查项，**不是本次冻结了新的协议、存储表、自动搜集行为或界面版本**。

## 3. 技术选型

### 3.1 主路线
- **业务/系统主语言：Rust。** 领域规则、权威状态、持久化服务、操作生命周期、安全执行边界和平台适配接口。
- **桌面框架：Tauri 2。** 提供桌面 Host 和受控前后端通信。
- **前端：React + TypeScript。** PC 工作界面、复杂交互、画布和多视图。
- **画布起点：React Flow（`@xyflow/react`）**，作为可替换的视图适配层；对象/关系模型不得依赖画布组件。
- **结构化本地存储：首版优先评估 SQLite。** 在 PC-0 验证事务、迁移、恢复和并发访问后确定最终方案。
- **第一交付平台：Windows。** macOS/Linux 后续按平台契约逐项验证。

### 3.2 选择理由与约束
- 不因 Android 使用 Flutter 就把 Flutter 定为 PC UI；既有 Flutter/Dart 代码逐模块评估复用。
- Tauri 的系统 WebView、打包、更新、无障碍和画布性能必须在 PC-0 实测；若存在不可接受的硬性阻碍，再基于证据评估 Electron。
- Rust 是领域主语言不意味着所有平台 API 都用纯 Rust 实现；OS 特有能力通过小而明确的 Host/Adapter 封装。
- 不同时维护两套 PC UI 技术路线，不提前为所有平台做抽象而拖慢首版。
- 用户已授权开始 PC 端技术施工，具体 UI 后续细化。对 WEX Android 的核心/验证接口作限时快速复用判断，能直接复用则接入；不为迁移旧 Flutter/Android 适配长期审查或延误开发。新桌面源码与验证边界见 `apps/desktop/README.md`。

同机 DeepSeek Harness（DSH）通过官方 ACP、SDK/headless 接口作为可选外部 Agent 执行者仍属接入候选，未确定为 0.1.1 安装依赖。WEXPC 保留项目状态、范围隔离、权限与证据责任；Windows 真实适配尚未验证。

## 4. 领域架构与状态边界

- 稳定对象身份与关系分离；父级、分类、访问权限、画布位置不是同一个概念。
- Rust 应用/领域服务是正式业务状态的权威写入口；React 只持有展示状态、选择状态和未提交草稿。
- Tauri command/event 是受校验的传输边界，不应承载第二套业务规则。
- 平台 Host 管理系统权限、凭证和进程能力；业务授权不能替代操作系统权限。
- 本地工作数据默认本地保存；代码、构建产物、密钥和环境变量不得因账号登录而自动上传。
- 操作成功不等于验证通过；未知结果不能自动重试；证据必须能关联到实际操作和目标版本。

### 4.1 外部 Agent 体系参考与当前研究边界（2026-10-25）

以下是外部架构研究方向与 WEXPC 已确认原则的关系，不是已完成集成、已冻结的实现选型，也不增加 0.1.1 交付条件。

- **DeepSeek Harness（DSH）**：除本文件 §2.4 已列的工具执行链路外，重点研究 Cordis 的服务/插件组合、可替换运行组件（包括 Agent Loop、模型适配、工具注册）、生命周期与配置修改机制。欣赏并研究其可修改性，不等于决定照搬 Cordis、采用 DSH 源码或允许任何插件绕过 WEX 权限/状态权威。
- **NousResearch Hermes Agent**：重点研究 Agent 决策循环、长期任务委派、持久角色/Bot Profile、跨会话恢复与经验积累。Agent 单次工具循环不等于持续任务；岗位/角色、Agent 实例、模型、会话、任务和权限应保持概念边界，秘书与主 AI 可以由同一 Agent 复任，不写死成两个永久角色。是否引入 Hermes 模块、怎样接线均待专项核实。
- **WEXPC 自有体系**：仍以本文件的 Rust 领域状态、连接与调度、授权、任务/回执和适配式上下文设计方向为依据。Cordis 的插件服务 Context、Hermes 的模型上下文管理与 WEX 所讨论的适配式 Context 不能因为同名而混同。后者的具体语义和实现仍需结合正式 WEX 设计继续研究，不以外部项目的架构直接替换。
- **体系适配能力 / 公共策略适配库**：这是之前讨论的后续研究课题，目前尚未充分研究。不能将它写成已确认的公共策略数据库、Skill 架构、版本排期或本批施工任务；Skill 是否及如何作为其载体，也未决定。
- **架构演进与返工**：继续推进已确认的 0.1.1 功能；深入研究外部机制后，可以基于可复现的差距做局部或跨模块调整。修改前逐项审查契约、调用者、持久状态、权限、兼容性、运行路径和回归验证；不得为了避免返工提前冻结，也不得仅因外部方案优秀便推翻已实现能力。研发建议不自动变成产品要求。

本节仅记录研究焦点与已明确边界，不宣称这两个项目在 WEXPC 实际环境中已完成源码级兼容性、Windows 集成或性能验证。


## 5. 0.1.1 首版目标、开发批次与验收

### 5.1 已确认的首版使用结果

用户安装并打开 Windows 版 WEXPC，配置可用的 AI API 和模型，选择 WEX PC 版或 Android 版的真实代码项目并完成适用授权后，可通过普通对话或软件开发工作入口，让 Agent 阅读项目、修改多处代码与文件、调用本机已有或外置的工具链运行/测试/编译、读取错误继续修复，查看差异、结果和证据，并按授权使用本地 Git 与 GitHub 完成相应操作。用户可在轻项目管理界面建立/切换项目、记录目标与约束、拆分和查看任务、指派多个 Agent 承担不同施工项，查看各自进度、修改、失败与交接；多个 Agent 在授权范围内可分别执行和汇总结果，不以轮流改名的单个 Agent 冒充多 Agent。用户离开对话、重启应用或中断一次工作后，能够从保存的项目目标、任务分派、已做的修改、执行结果和未完成事项接续开发。首版应足以让用户**用 WEXPC 继续开发 WEX 的 Android 版和 PC 版**，而不是只能演示一条命令或单文件操作。

“持续开发”要求在已确认目标与权限内连续推进，并记录真实状态及需要用户决策的阻碍；不要求用户对同范围的每一步反复发送“继续”。它不等于在应用关闭或电脑休眠时无条件后台执行，也不赋予 Agent 未经授权的新范围。

0.1.1 的轻项目管理至少覆盖项目目标/约束、任务清单与状态、Agent 分派、操作与版本证据、阻碍和接续入口；可分别管理 WEX Android 和 PC 的真实项目。多 Agent 施工要求多个可区分的执行身份与会话承担分派任务，能在互不冲突的不同任务上并发施工，并保留明确交接，并把结果关联回项目；多个施工者不能同时修改同一处，系统须以范围占用和执行隔离实际阻止重叠写入，并检查集成冲突。具体并行调度上限、模型组合和隔离实现待设计，不能以单 Agent 演示或单项目样例充当产品上限。主 AI 分配、可持久任务卡、独立验证与审查/修复流转属于 0.1.1；跨多个项目**同时**自治调度、自由画布和多视图接线仍可后置；画布和多视图的版本归属待确认。

### 5.1.1 0.1.1 岗位、角色与 Agent：首版最低交付契约（2026-10-26 补齐）

本节明确 §2.2、§2.7.2、§2.7.8 已确认的首版责任边界；不把完整角色形象、个性化长期记忆或视觉编辑器提前纳入首版。

- **角色（Persona）**：对外交流身份、沟通习惯或表现偏好，可作为配置；不是资源授权、岗位职责或 Agent 唯一身份。0.1.1 至少可保存与选用基础角色配置，复杂形象、TTS、长期人格记忆后置。
- **岗位/职责（Duty）**：可配置的工作责任和允许提出的受控动作；至少可表达项目主 AI、施工、审查、验证与可兼任的秘书职责。一个 Agent 可兼任多个职责，同一岗位可由多个 Agent 承担，不得固定为单一模型或永久固定成员。
- **Agent 实例（Executor）**：稳定独立的执行身份、所选 Connection/Provider/Model、会话及运行状态；同一模型可服务不同 Agent，模型更换不抹除 Agent 身份或既有证据。
- **权限（Authority）**：OS、连接器启用状态、项目/Context/资源范围、任务执行范围、操作类型与自动/询问/拦截策略共同生效。职责是能力约束而非越权凭证，兼任岗位不能合并无关项目的授权；审查可有较广的有效只读范围但不因此有写入权。
- **最小用户操作**：创建成员与基础角色配置 → 选择模型 → 为成员分配一个或多个项目/用户级职责 → 分派任务 → 查看当前职责、会话、执行范围与结果 → 调整/撤销职责和授权；撤权应影响后续未派发操作，历史证据保留。
- **首版验收**：同一 Agent 兼任两项岗位但权限不自动合并；两个 Agent 共用模型仍有独立身份与执行记录；审查岗位不能凭岗位名写代码；变更职责不得改写已保存的工具回执；普通对话不用先创建任务或任命项目主 AI。

### 5.1.2 三系统贯通：轻项目管理 × Dispatcher × 多 Agent 施工

三者是 **0.1.1 的一条端到端用户能力**，不能分别以任务草案、单次模型工具调用和几个 Agent 名称作为完成证据。

| 子系统 | 首版最低交付 | 不可冒充为完成 |
| --- | --- | --- |
| 轻项目管理 | 建立/切换真实项目，保存目标、约束、基准引用、任务卡、验收条件、修改范围、负责人、依赖/阻碍、状态、关联会话、执行/审查/验证证据；重启后可查看、继续和修订任务 | 只建项目/任务草案，或仅在聊天中陈述任务计划 |
| 程序化 Dispatcher | 对已批准任务完成接收、路由、排队、实际派发、执行状态转移、资源范围占用、冲突阻止/升级、回执归档、失败及结果未知处理、审查/验证交接、恢复后状态核对；普通对话工具调用可不经任务系统 | 单纯 Task 状态机、模型自述“已派工”、某个主 AI 冒充调度器，或仅有一次工具执行回执 |
| 多 Agent 施工 | 至少两个稳定不同的 Agent/会话在互不冲突范围执行真实文件/命令/Git 工具；各自权限隔离，可并发且重叠写入必须被阻止；结果回写各自任务卡，经审查/验证后交接或修复 | 并行聊天、顺序轮换一个 Agent、仅有 Agent 名单、无共享资源协调的同时写入 |

**最小贯通场景**：选择一个真实 WEX PC/Android 代码项目 → 配置主 AI、两个施工 Agent 与审查/验证职责（允许兼任）→ 主 AI 形成并发布两张具有真实修改范围的任务卡 → Dispatcher 在权限内派工并阻止重叠写范围 → 两个施工 Agent 分别操作文件/命令/Git，产生实际版本及回执 → 审查与验证根据真实证据通过或退回同范围修复 → 状态和未完成工作持久保存 → 中断/重新打开后先核对未知结果，再继续剩余任务。再用另一个真实代码项目验证首版不被单一演示样例锁死。

**不可变约束**：已派发、工具成功、独立验证成功及任务完成分别记状态；结果未知不得自动重试副作用；任务范围和项目关联本身不授予目录/终端/GitHub 权限；用户新增范围、新权限或架构需求变更仍须确认。首版无需跨多个项目同时自治调度、完整自由画布、完整语音或悬浮角色面板。

### 5.1.3 持续推进、职责授权、事实关联和中断接续的验收补充（2026-10-26）

本节把 §2.7 与 §5.1.1～§5.1.2 已确认的工作能力整理为施工契约，不冻结数据库表结构、单独守护进程选型或自动运行时刻。

**A. 主 AI 的连续工作与任务推进**
- 主 AI 可依据项目目标、任务卡、已有证据和阻碍形成计划并提议拆分；已确认的计划发布为有版本的任务，不因一次 AI 回复就标记任务完成。
- Dispatcher 负责确定性接收、排队、交付给指定 Agent、持久状态转移和后续唤醒/续接；主 AI 基于实际回执决定继续同范围修复、调整后续分派、申请新授权或升级用户决策，不能由 Dispatcher 擅自替主 AI 做技术判断。
- 在有效授权和已确认目标内，任务可以跨多个模型回合继续；用户无需每小步重复发送“继续”。没有可执行工作、权限变化、发生冲突、达到预算/时限或需要新的产品决策时进入阻碍/待决定状态，不假装无限自治。

**B. 岗位、角色、模型与授权的双向校验**
- Agent 承担岗位后，可见的职责/模型/会话/任务范围分别记录并可变更；角色只定义表现与交互偏好，岗位限定责任，权限另行检查，不得由职务名称、项目归属或模型复用自动派生本地文件、进程或 GitHub 权限。
- Dispatcher 每次派发前校验当前 Agent 身份及岗位适用性、任务有效版本/状态、有效项目及资源范围、Connection 启用、OS 授权、工具动作和执行策略；Host 在实际有副作用操作前再次进行有效权限与版本检查。
- 审查岗位默认不取得施工写权限；同一 Agent 兼任施工和审查时，必须按当前任务职责隔离权限与操作记录，不得把自我审查自动视为独立验证。

**C. 可追溯事实链及权威归属**
- 至少能从项目/任务卡定位任务版本、发布和指派责任、Agent 及会话、Dispatcher 派发/尝试、操作意图、工具请求、回执、修改文件/Commit/环境版本、审查与验证结论、待用户决定事项；也能从一次执行回执反向定位其任务及目标范围。
- 项目与任务状态由 Rust 领域服务维护；Host 记录可信外部工具/OS 结果，React 呈现状态。模型生成的解释、人工备注、工具事实、审查判断、独立 Verify、最终验收均为不同来源，不能互相替代。
- 草案 → 已发布/待派发 → 排队/已派发 → 执行中 → 待审查 → 待验证 → 已完成为参考流程；阻碍、取消、失败、结果未知、退回修复是明确分支。**这是语义和验收参考，不冻结枚举名或状态转换表。**任何历史修订不可静默覆盖已有回执。

**D. 停止、故障、权限撤销与恢复**
- 用户停止生成、取消排队任务、取消在跑工具和应用退出属于不同操作：停止后不得派发尚未开始的新操作；已发出的外部操作应核实能否取消，不能仅把 UI 标记为停止。已发生的文件/Commit 副作用不会因停止自动回滚。
- 对超时、进程崩溃、断网、关闭/重启、Agent 失联、权限撤销和持久化失败，记录最后可信状态与剩余任务；已执行但无可信结果的写入进入“结果未知”及人工/可信工具核对，**不得自动重试**。
- 重新进入项目后，先恢复项目/任务/职责/授权状态和证据索引，再核对外部版本与未决结果、释放或复核占用，才能重新派发符合当前授权及任务版本的工作。权限撤销禁止后续派发，但不伪造历史副作用已撤销。
- 正常重启后有效的授权遵循持续授权规则；系统重装、卸载重装按 §5.6 不自动恢复凭证与许可。无需保证应用关闭或 Windows 休眠时持续运行。

**E. 0.1.1 联合验收场景（验收时执行，当前仅定义）**

| 编号 | 必须验证的具体行为 | 不合格示例 |
| --- | --- | --- |

0.1.1 的实现细节仍可按实际约束调整；上述验收不能降低 §2.4 的通用终端/多文件能力，也不将后置画布、完整语音、悬浮角色形象或跨项目同时自治调度提升为首版要求。

### 5.6 用户可选目录、文件保留与重装安全边界（当前无账号系统阶段）

依据：2026-10-25 本次用户确认。目标是让用户自主安排安装、数据和环境位置；系统故障或重新安装时尽量复用资料与已下载内容，减少重复下载和重建。**文件保留/复用与身份认证/授权恢复分别处理**。此项属于当前 Windows 安装与恢复流程；不据此增加账号系统、云同步或跨设备凭证恢复，也不推定未来有账号后可以自动恢复权限。插件/环境目录规则适用于相应能力实际交付时，不因此将完整插件市场或所有环境下载管理自动新增为 0.1.1 承诺。

| 内容 | 已确认的目录与保留行为 | 恢复边界 |
| --- | --- | --- |
| WEXPC 程序本体 | 安装包安装时允许用户选择安装目录 | 安装位置不等于项目目录、数据目录或授权范围；程序重新安装不自动信任旧安装的身份与授权 |

| WEXPC 管理的开发环境、下载缓存 | 用户可设定存放位置；恢复时检查已有内容，优先复用、修复或补齐缺失项 | 文件仍在不代表系统组件、注册或依赖已就绪；显示可用/缺失/需修复状态，不承诺免检查即可运行，也不因重装默认重新下载全部 |
| 用户已安装的工具链 | 登记并使用用户选择的现有位置，不强制迁移或重复安装 | 系统重装后重新检测路径、版本和依赖；环境路径的恢复不授予 AI 执行权 |

| AI、目录、工具、连接及会话等有效授权 | 历史授权记录可留作审计，不能作为重装后的有效许可 | 重装系统或卸载重装后须重新授权；旧 GitHub 全局开关、目录许可、执行策略与待审批/已批准操作不得自动重新生效，保留历史记录不自动派发任务或重放工具 |

**场景区分：**
- 正常关闭后重新打开、常规应用/请求中断，继续遵守 §5.1/§5.4 的状态保留与有效授权内接续要求；不把本节扩大成每次启动都重新输入 Key 或重新授予每条命令权限。
- 重装系统、卸载后重新安装，属于重建本机使用关系：可以重新选择旧资料/插件/环境目录，但凭证由用户重新配置、权限由用户重新授予；即使旧数据目录完整，也不能仅凭路径、配置或历史审批恢复访问。
- 普通版本升级与卸载重装分别定义，不能让升级机制绕过本节边界；升级保留行为、安装身份识别和失败修复机制仍待工程设计/验证。
- 完成重新配置与重新授权后，同一已批准范围内仍按持续授权和执行策略工作，不退化为永久逐文件/逐命令审批。

**待设计细节**：首次安装与设置页分别怎样选择目录、默认位置与可选非系统盘、一个根目录或分别配置、目录迁移/不可用/盘符变化/版本不兼容、卸载普通资料保留/清除交互、重装识别和凭证清理实现。用户可选目录及重装后不得自动恢复凭证/权限是已确认方向，不再列作待确认；不得以目录迁移为由擅自改变授权或移动真实项目。具体恢复不能依赖“没有账号所以不需要隔离”的假设。

**验收场景（尚未执行）：**
1. 安装时选择自定目录，并配置数据/插件/环境位置；正常重启按原有效设置使用，不要求重复配置。
2. 在新安装中明确选择原数据目录，项目/对话/任务/证据可按兼容性恢复；旧 Key/Token、插件密钥引用、全局开关、目录及工具许可均不自动生效。
3. 旧目录含历史批准和未完成任务时，可查看事实与待办，不能自动执行旧工具或续跑未知副作用；重新配置/授权后核对真实状态再接续。
4. 卸载重装但 Windows 凭证库仍有旧条目时，也不能自动恢复访问；需验证新安装不静默采用旧引用。
5. 保留的环境/插件完整时优先检查复用，缺系统组件、部分下载或盘符变化时明确报告并提供修复流程；未重新授权不执行环境脚本或插件。
6. 对比正常重启与重装场景，证明既没有让重装继承旧权限，也没有误伤正常会话及持续授权保留。系统重装、卸载重装、普通升级分别留证。

本节为需求与验收规范，当前代码仍使用 Host 提供的 `app_data_dir` 和 Windows Credential Manager；可选目录、重装识别、敏感引用失效和恢复界面尚未实现或验收。不能用目录设置文档更新或凭证存在/不存在推断安全边界已经落实。

### 6.3 PC 项目持续开发：必须具备的端到端用户体验

用户能够在 WEX PC 内选定一个工作 Context / 软件开发项目，提交目标、背景、约束、正式需求和需要确认的设计问题。主 AI 结合权威项目记录提出计划及工作项；需要用户决定的范围/架构/产品方向交由用户确认。随后在有效权限及已批准工作范围内，由程序 Dispatcher 登记、分发、追踪及恢复任务，由被分配的执行者对真实文件、本地 Git 或远端 GitHub 做实际修改和提交；审查者针对**对应版本**的规范、Diff、产物和证据独立审查，测试/构建通过实际工具留证；失败时仅依既定规则转交同范围修复，无法判定、越界或新增决策时升级给主 AI / 用户。完成必须区分报告、提交、审查、技术验证和 Windows 实际验收。

这条流程支持**无人逐项催促的连续推进和中断恢复**，但不意味着持续消耗主 AI Token、不受控执行任意命令、自动修改用户要求，或 WEX 关闭/PC 休眠后仍能无条件工作。运行条件、持久状态、幂等/结果未知、副作用核对、重启后恢复、人工接管和成本可见性必须设计和验证。

关键身份与记录至少要在领域上区分：Project/Context Baseline、State Snapshot、Task/Card、Role Assignment、Session、Execution Attempt、Dispatcher Event/Receipt、Review Record、Evidence/Verification、外部 Commit/Run、User Decision。这里**不冻结**数据库表名、字段、消息结构或物理目录。多成员、多轮施工和多份审查须允许未来扩展，不把首条测试样例作为永久上限。

原设计中主 AI 自动唤醒曾明确**暂不进入 Android 首期**：PC 要重新审议是否/何时需要，而不是推定已授权自动唤醒。初始方案可保留主 AI 按用户主动对话及定期检查介入的机制，但该实施细节须另行确认，不能误写为 PC 永久限制。

- **验收关键行为**：在 Windows 的 WEX PC 与 Android 真实项目上，用户确认目标及适用权限后，系统可建立轻项目任务、分派多个 Agent 施工、连续修改并执行真实工具、保存各执行者的任务进度与版本关联证据、重启后接续，并在失败或越界时升级决策；无需每一步重新输入“继续”。独立 AI 审查是首版协作流程的一部分，其结论不能代替实际测试和构建证据。运行中的模型、连接器、项目、证据、权限均可分别检查，独立查看失败原因。

- Android/Flutter UI 就是 PC UI；
