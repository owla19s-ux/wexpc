# WEX PC 产品、功能与技术基线

- 状态：WEXPC 当前产品与技术**工作基线（已进入 main，尚未整体冻结）**。PC 优先及 0.1.1 的轻项目管理、Agent/多 Agent 施工与本地工具能力已确认；新增阶段划分、具体选型及尚未收敛的交互细节仍分别标注待验证或待确认，不因写入本文自动获批。
- 适用仓库：WEXPC。
- 本文不代表所列功能已经实现，也不代表 Windows 实机验收通过。
- Android 文档和代码仅作为已确认业务语义、架构、安全原则及可复用模块的参考；PC 的 UI 技术与交付顺序由本基线决定。

## 1. 产品方向

WEX 当前优先建设 PC 产品，首期目标 Windows。产品长期以统一工作对象和自由画布为重要交互方向，软件开发是第一个落地的工作模式；自由画布与多视图接线不作为 0.1.1 首版完成条件。聊天记录不是唯一事实源；对象、关系、执行状态和验证证据应独立保存。

此次变更是 WEX **整体开发重心由 Android 转至 Windows PC**，不是把 Android 0.1.1 的精简版搬上 PC，也不是创建业务语义不相容的新产品。Android 0.1.1 中因阶段成本而后置的产品能力必须重新纳入 PC 完整范围审视，但原来只是讨论、候选或后续研究的内容不会因此自动成为已确认的首批交付要求。

PC 不等于把 Android 页面放大。Android 可提供连接器、安全边界、权限/撤权、操作生命周期、失败恢复、GitHub 回读核验等参考，但 Android 页面结构、Flutter 工程形态和旧版本顺序不约束 PC。

## 2. PC 产品功能范围（不等于全部在首个批次交付）

### 2.1 工作对象与画布

2026-10-24 当前施工重点：先根据架构整理仓库职责并建设核心/基础服务，优先 Space、Context 与轻项目管理。0.1.1 先提供基础的空间、可选分组、通用上下文、项目关联与持久恢复；UI 细节后续细化。该顺序不取消已确认的本地开发、多 Agent 并发、独立验证/审查与模拟器目标。

本节描述 PC 产品完整方向。0.1.1 先提供可操作的轻项目管理、对话、任务分派、多个 Agent 施工状态及证据界面；自由画布和多视图接线可在后续批次或版本完成，后置不等于删除对象与关系的扩展需求。
- 对象使用稳定 ID；对象内容、层级、依赖/一般关系、画布布局分别建模。
- 支持树形与网状关系，不能将整个数据模型限制为单一树。
- 自由画布支持创建、选择、编辑、移动、连接、分组、缩放和平移。
- 画布、表格、列表、树形、看板和详情视图读取同一权威数据。
- 支持自动保存、撤销/重做、历史恢复和数据导出；具体事务与历史契约在实现前定义。
- 无 AI 连接时仍能手动组织本地工作数据。

### 2.2 AI 秘书与模型
- 管理多个 API 连接、服务商和模型；优先验证 DeepSeek 与 OpenAI 兼容 API。
- 秘书模型与专业执行模型可分别配置；不将 AI 角色固定为不可扩展的名单。
- 对话可引用工作对象、画布区域、项目和任务，但不取代正式业务状态。
- AI 对结构、文本或代码提出变更时，支持预览、调整、接受和拒绝。
- 清晰区分用户已确认内容、AI 建议、待确认、排队、执行中、成功/失败、结果未知与独立验证通过。
- 执行策略统一为自动执行、询问后执行、拦截；凭证权限、OS 授权和操作安全检查仍独立生效。
- 支持编辑消息后重新生成、生成期间追加消息排队；不得把重发消息误当作撤销已发生的外部操作。

### 2.3 API、连接器与权限
- 连接、服务商、模型、会话身份和工具能力分开建模。
- 凭证与普通配置分离；密钥不得进入日志、对话内容或普通业务数据库。
- 连接器统一声明能力、输入输出、授权要求、超时、取消、错误与结果未知语义。
- 连接测试、模拟响应、真实服务商响应必须明确区分。
- 用户可以查看、撤销和限制连接权限；撤权不能只改 UI 标记而不影响后续请求。

### 2.4 本地软件开发链路（WEXPC 0.1.1 明确需求）
- WEXPC 0.1.1 必须让用户配置 AI API 后，在 Windows 本机选定项目及相应授权范围，由 AI Agent 通过 WEX 的受控工具调用操作本地文件与代码环境，完成基础的读取、修改、运行、测试和编译，并根据真实工具反馈继续处理或向用户报告。普通对话与软件开发工作模式均能使用适用的本地工具能力；软件开发模式负责持续任务组织，不能成为每次普通工具调用的前置。
- 编译器、解释器、语言 SDK、构建工具与项目依赖可以使用用户本机安装或外置的现成环境。WEX 提供环境发现/选择、调用、进程管理和结果接线，不要求自行打包所有语言的完整工具链；具体环境支持范围与安装指引按实际适配记录，不把单一语言或单一项目样例当产品上限。
- 用户明确选择项目目录后，在授权范围内读取和修改文件。
- Windows 本地环境纳入 Android SDK 与模拟器：选择/启动设备、安装运行构建、执行适用测试并读取日志，失败进入同一修复链；模拟器验收与真机验收分别记录。
- 集成本地 Git 状态、差异、分支、提交、冲突与回读。
- 支持从 AI 工具调用或用户界面启动项目已有的运行、构建、测试和打包命令；记录实际命令、工作目录、所用环境、进程状态、退出码、日志摘要、产物位置和时间。进程完成或失败的结果回到 Agent 上下文与用户可见界面，便于继续修复或复核。
- 软件开发模式需要较完整的本地 Agent 能力：在用户明确授予的项目/工作目录及可用代码环境内，可连续调用文件操作、终端进程、本地 Git 与适用连接器，运行项目所需的多步骤命令并读取结果；不把每条命令、每个文件或每次工具调用都变成逐项重新授权。用户可查看、调整和撤销授权，执行策略可设为自动执行、询问后执行或拦截；对授权外范围和新权限需求应提示用户决策。
- 本地进程具备可见状态、超时、取消、失败报告和审计记录。命令能力的范围按用户授权与执行策略决定，不能由单一演示项目固化成永久的命令白名单；也不因较宽能力推定默认全盘访问。
- 区分外部请求已接受、已派发、结果已知/未知、结果已持久化和独立核验通过。
- 验证时先在 Windows 本地打通一条真实项目闭环：选择项目与代码环境 → Agent 读取/修改 → 运行或测试/编译 → 获得真实结果 → 依据反馈继续或报告。验收要同时覆盖命令失败、环境缺失、用户取消、超时、权限撤销和重新进入项目后的状态。远程开发、容器、云端 CI 属后续连接器，不作为这条本地闭环的替代。

DSH 参考的是“模型 API → Agent 工具调用 → 本地文件/终端执行 → 输出和退出状态返回模型”的实际机制（参见 [DeepSeek Harness 官方使用指南](https://deepseek-harness.github.io/deepseek-harness/en/guide/quickstart)与[官方 Shell 文档](https://deepseek-harness.github.io/deepseek-harness/en/reference/subsystems/shell)）。这只是能力和交互参考，不表示 WEXPC 已采用 DSH 的代码、插件架构或权限默认值；WEXPC 的运行环境、授权和回执仍按本基线独立设计。

### 2.5 GitHub 与验证
- 首版实现真实 GitHub 连接、仓库读取、受控修改、提交、回读和内容核验。
- 遵循正式授权范围；不能以 AI 生成的建议替代用户授权。
- 不得把 GitHub 的验收结果外推到其他托管平台。
- 外部写入结果未知时，不得盲目自动重试可能产生重复副作用的操作。

### 2.6 语音
- 鼠标与语音是目标主要交互方式，键盘和快捷键作为补充。
- 语音指令结合当前选中对象和已确认上下文；关键范围不明确时请求澄清。
- PC 产品方向包括基础语音输入；其 0.1.1 验收深度待确认。识别引擎、TTS 和角色表现另行评估，不作为本地软件开发闭环的前置。

## 3. 技术选型

### 3.1 主路线
- **业务/系统主语言：Rust。** 领域规则、权威状态、持久化服务、操作生命周期、安全执行边界和平台适配接口。
- **桌面框架：Tauri 2。** 提供桌面 Host 和受控前后端通信。
- **前端：React + TypeScript。** PC 工作界面、复杂交互、画布和多视图。
- **画布起点：React Flow（`@xyflow/react`）**，作为可替换的视图适配层；对象/关系模型不得依赖画布组件。
- **结构化本地存储：首版优先评估 SQLite。** 在 PC-0 验证事务、迁移、恢复和并发访问后确定最终方案。
- **第一交付平台：Windows。** macOS/Linux 后续按平台契约逐项验证。

### 3.2 选择理由与约束
- 不因 Android 使用 Flutter 就把 Flutter 定为 PC UI；既有 Flutter/Dart 代码逐模块评估复用。
- Tauri 的系统 WebView、打包、更新、无障碍和画布性能必须在 PC-0 实测；若存在不可接受的硬性阻碍，再基于证据评估 Electron。
- Rust 是领域主语言不意味着所有平台 API 都用纯 Rust 实现；OS 特有能力通过小而明确的 Host/Adapter 封装。
- 不同时维护两套 PC UI 技术路线，不提前为所有平台做抽象而拖慢首版。
- 用户已授权开始 PC 端技术施工，具体 UI 后续细化。对 WEX Android 的核心/验证接口作限时快速复用判断，能直接复用则接入；不为迁移旧 Flutter/Android 适配长期审查或延误开发。新桌面源码与验证边界见 `apps/desktop/README.md`。

同机 DeepSeek Harness（DSH）通过官方 ACP、SDK/headless 接口作为可选外部 Agent 执行者仍属接入候选，未确定为 0.1.1 安装依赖。WEXPC 保留项目状态、范围隔离、权限与证据责任；Windows 真实适配尚未验证。

## 4. 领域架构与状态边界

- 稳定对象身份与关系分离；父级、分类、访问权限、画布位置不是同一个概念。
- Rust 应用/领域服务是正式业务状态的权威写入口；React 只持有展示状态、选择状态和未提交草稿。
- Tauri command/event 是受校验的传输边界，不应承载第二套业务规则。
- 平台 Host 管理系统权限、凭证和进程能力；业务授权不能替代操作系统权限。
- 本地工作数据默认本地保存；代码、构建产物、密钥和环境变量不得因账号登录而自动上传。
- 操作成功不等于验证通过；未知结果不能自动重试；证据必须能关联到实际操作和目标版本。

## 5. 0.1.1 首版目标、开发批次与验收

### 5.1 已确认的首版使用结果

用户安装并打开 Windows 版 WEXPC，配置可用的 AI API 和模型，选择 WEX PC 版或 Android 版的真实代码项目并完成适用授权后，可通过普通对话或软件开发工作入口，让 Agent 阅读项目、修改多处代码与文件、调用本机已有或外置的工具链运行/测试/编译、读取错误继续修复，查看差异、结果和证据，并按授权使用本地 Git 与 GitHub 完成相应操作。用户可在轻项目管理界面建立/切换项目、记录目标与约束、拆分和查看任务、指派多个 Agent 承担不同施工项，查看各自进度、修改、失败与交接；多个 Agent 在授权范围内可分别执行和汇总结果，不以轮流改名的单个 Agent 冒充多 Agent。用户离开对话、重启应用或中断一次工作后，能够从保存的项目目标、任务分派、已做的修改、执行结果和未完成事项接续开发。首版应足以让用户**用 WEXPC 继续开发 WEX 的 Android 版和 PC 版**，而不是只能演示一条命令或单文件操作。

“持续开发”要求在已确认目标与权限内连续推进，并记录真实状态及需要用户决策的阻碍；不要求用户对同范围的每一步反复发送“继续”。它不等于在应用关闭或电脑休眠时无条件后台执行，也不赋予 Agent 未经授权的新范围。

0.1.1 的轻项目管理至少覆盖项目目标/约束、任务清单与状态、Agent 分派、操作与版本证据、阻碍和接续入口；可分别管理 WEX Android 和 PC 的真实项目。多 Agent 施工要求多个可区分的执行身份与会话承担分派任务，能在互不冲突的不同任务上并发施工，并保留明确交接，并把结果关联回项目；多个施工者不能同时修改同一处，系统须以范围占用和执行隔离实际阻止重叠写入，并检查集成冲突。具体并行调度上限、模型组合和隔离实现待设计，不能以单 Agent 演示或单项目样例充当产品上限。主 AI 分配、可持久任务卡、独立验证与审查/修复流转属于 0.1.1；跨多个项目**同时**自治调度、自由画布和多视图接线仍可后置；画布和多视图的版本归属待确认。

### 5.2 同一 0.1.1 版本内的施工批次（建议顺序，不是独立缩水版本）

| 批次 | 交付后用户可操作行为 | 对应验收与剩余边界 |
| --- | --- | --- |
| A：Windows 基础与轻项目管理 | 启动桌面程序、配置 API，创建/切换项目，记录目标、任务和进度并在重启后恢复 | Windows 启动/重启、配置与数据恢复；此批不宣称 Agent 开发闭环完成 |
| B：本地 Agent 工作链 | 对真实项目对话，授权读写文件并调用外置代码环境运行、测试、编译，读取失败后继续修改 | 分别核查权限、工具真实执行、取消/超时/环境缺失、进程退出和反馈；不把单一示例固化为产品限制 |
| C：多 Agent 施工与 Git | 将不同任务分派给多个 Agent，分别查看执行与交接；查看本地差异、提交，连接 GitHub 真实读写与核验，保留进度供接续 | 在 WEX PC 与 Android 项目分别验证多 Agent 实际施工、多文件/多轮修改、版本对应、冲突反馈、重启接续和异常升级 |
| D：首版集成与 Windows 交付 | 在同一界面完成配置、对话/任务、授权、操作、结果与恢复，取得可安装的 Windows 构建 | 对实际交付提交执行自动化、真实 API/GitHub、本机编译、Windows 安装运行与数据保留验收 |

批次 A～D 可按技术依赖调整先后和合并测试，但 0.1.1 的首版使用结果不能因分批而缩减。每批记录已实现、自动化、真实服务、Windows 构建与实机验收，以及尚未覆盖的首版要求。

| **0.1.5：更多工作模式与生态** | 在软件开发之外提供小说等工作模式，扩展公共知识/结构化工具库、角色表现与声音、账号和可选云服务；每项有独立启用、数据与权限边界 | **长期方向的候选聚合，版本归属待确认**；原 PC 文档的 0.1.5/发布窗口是假设，不能写成已批准首发承诺 |

**跨版本规则**：Connection/Connector、权限、Dispatcher、状态与回执属于通用底座；软件开发只是第一个工作模式，不能把全部 Context 固定为代码项目。用户级秘书、语音、浏览器、搜索、公共库和云端功能的具体颗粒度及版本归属须在确认表时逐项核对。0.1.1 可选择/保存多个真实项目，并在所选项目内分派多个 Agent 施工；跨项目同时自治调度的版本归属待确认。

### 6.3 PC 项目持续开发：必须具备的端到端用户体验

用户能够在 WEX PC 内选定一个工作 Context / 软件开发项目，提交目标、背景、约束、正式需求和需要确认的设计问题。主 AI 结合权威项目记录提出计划及工作项；需要用户决定的范围/架构/产品方向交由用户确认。随后在有效权限及已批准工作范围内，由程序 Dispatcher 登记、分发、追踪及恢复任务，由被分配的执行者对真实文件、本地 Git 或远端 GitHub 做实际修改和提交；审查者针对**对应版本**的规范、Diff、产物和证据独立审查，测试/构建通过实际工具留证；失败时仅依既定规则转交同范围修复，无法判定、越界或新增决策时升级给主 AI / 用户。完成必须区分报告、提交、审查、技术验证和 Windows 实际验收。

这条流程支持**无人逐项催促的连续推进和中断恢复**，但不意味着持续消耗主 AI Token、不受控执行任意命令、自动修改用户要求，或 WEX 关闭/PC 休眠后仍能无条件工作。运行条件、持久状态、幂等/结果未知、副作用核对、重启后恢复、人工接管和成本可见性必须设计和验证。

关键身份与记录至少要在领域上区分：Project/Context Baseline、State Snapshot、Task/Card、Role Assignment、Session、Execution Attempt、Dispatcher Event/Receipt、Review Record、Evidence/Verification、外部 Commit/Run、User Decision。这里**不冻结**数据库表名、字段、消息结构或物理目录。多成员、多轮施工和多份审查须允许未来扩展，不把首条测试样例作为永久上限。

原设计中主 AI 自动唤醒曾明确**暂不进入 Android 首期**：PC 要重新审议是否/何时需要，而不是推定已授权自动唤醒。初始方案可保留主 AI 按用户主动对话及定期检查介入的机制，但该实施细节须另行确认，不能误写为 PC 永久限制。

### 6.4 阶段目标与状态约束

- **产品完整范围**：上表继承或恢复原已确认的 P/M 能力；原候选/研究继续保持原身份。
- **0.1.1 分批**：§5 的 A～D 是一个版本内的施工安排，不是 PC-0/PC-1 等额外产品版本；单批完成不等于首版完成。
- **0.1.1 本地开发能力**：§2.4 所述 AI Agent 经 API 与用户授予的较完整本地工具能力操作项目、调用可外置的代码/编译环境、连续运行/测试/编译并读取真实反馈，是用户明确的 0.1.1 需求；§5 的批次不改变该版本需求归属。
- **原 PC-0 / PC-1 / PC-1.1 / PC-2 标签**：此前用于技术和交付建议，现由 §5 的 0.1.1 使用结果与施工批次替代；旧标签不作为版本承诺。持续开发和状态恢复属于 0.1.1，多 Agent 施工在 0.1.1；跨项目自治调度及画布多视图在 §5.3 有候选版本归属，尚待确认；独立验证/审查属于 0.1.1。
- **验收关键行为**：在 Windows 的 WEX PC 与 Android 真实项目上，用户确认目标及适用权限后，系统可建立轻项目任务、分派多个 Agent 施工、连续修改并执行真实工具、保存各执行者的任务进度与版本关联证据、重启后接续，并在失败或越界时升级决策；无需每一步重新输入“继续”。独立 AI 审查是首版协作流程的一部分，其结论不能代替实际测试和构建证据。运行中的模型、连接器、项目、证据、权限均可分别检查，独立查看失败原因。
- **实现事实**：WEXPC 现有 Flutter/Rust 迁入代码是参考资产，不代表以上 M 能力已经接通。Tauri/React/React Flow/SQLite 属本文件的技术路线与验证计划，非既有产品已完成事实。
