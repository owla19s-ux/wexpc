# WEXPC 0.1.1 施工路线与链路验收计划

- 状态：**工程执行计划（D 域），2026-10-26 建立**；非新产品基线，不替代已确认的 [PC 产品与技术基线](PC-PRODUCT-AND-TECH-BASELINE.md)。
- 产品版本：固定 **0.1.1**。本文的 P1～P6 是施工批次，**不是** 0.1.1～0.1.6 产品版本。
- 来源：PC 基线 §2.4、§2.7、§4、§5.1～§5.6，尤其 §5.1.1（岗位与角色）、§5.1.2（三系统贯通）、§5.1.3（持续工作及 R-01～R-08）；工程和 GitHub 操作遵循 [DEVELOPMENT-WORKFLOW](DEVELOPMENT-WORKFLOW.md)。
- 当前证据边界：已有 Tauri/React + Rust 服务、部分 API 对话/工具回合、GitHub 文件读写、授权目录读取与独占创建、任务草案、执行检查点/回执等源码；**不等于** Windows 实机验收，也不等于完整多 Agent 施工已实现。本文是未来施工组织及缺口计划，不将拟实现写成已完成。
- 当前验证安排（2026-10-26 最新指令）：**能在当前本地环境执行的测试直接执行**，替代此前“10 月底前不运行本地构建/测试”的临时限制；GitHub Actions 仍暂停至 2026-10-31（含），不自动恢复 CI。Windows、真实服务及实机证据仍分别登记，历史结果不得套用于新提交。
- 三域隔离：WEX 用户产品能力为 P 域；WEX 产品内 Agent 开发工作模式为 M 域；**我们开发 WEXPC 的工程施工**为 D 域。本文的施工分工不是产品内 Dispatcher 的实际执行证据。

## 一、施工总目标与非目标

首版应允许用户在 Windows 上选择真实 WEX PC 或 Android 代码项目，配置 AI API/模型、GitHub 和项目授权，建立任务并让主 AI 分派给多个独立 Agent。在**不重叠的写入资源范围**内，Agent 可以连续操作多处文件、使用已选本机或外置环境运行/测试/编译、本地 Git/GitHub，并读取真实反馈继续修复；审查/验证结论、版本与回执持久关联，程序中断后先核对结果再恢复。

普通对话可直接使用适用且已授权的工具，不要求先创建项目、Task 或启用主 AI。Connection/Connector、Dispatcher、权限/审批、证据/状态和 Host/Tool Runtime 保持分层。Dispatcher 是确定性程序机制，不是某个模型或任务状态机。

**不属于 0.1.1 首次完工门槛**：自由画布完整交互、多视图、悬浮角色形象、完整个人长期记忆、多个项目同时自治调度、远程 CI/容器、跨设备遥控。上述仅按正式基线保留未来范围；不将后续研究的体系适配库/DSH/Hermes 接入固化成先决条件。

## 二、六个相互衔接的施工批次

| 批次 | 目标 / 主要改动 | 完成判定（源码集成 + 当前本地可测即测，平台验收另记） | 不允许用来冒充完成 |
| --- | --- | --- | --- |
| **P1 本地开发工具闭环** | 授权目录下多文件读取/新建/版本化修改；安全替换；本地 Git 状态、Diff、分支、Commit；通用受控进程/终端；环境发现/选择；模型工具反馈及回执 | 一个真实项目中模型连续修改多文件、运行已授权项目命令、读取退出码和输出并再次修复；Git/GitHub 可核验；回执 durable | 只会读取/新建单文件；固定 Cargo test/fmt 两条命令；仅有未暴露的修改预检 |
| **P2 轻项目与执行关联** | 项目目标与约束、任务卡版本、工作范围、受派 Agent/会话、尝试/事件/证据 ID、依赖/阻碍、接续状态；草案到发布到真实执行的关系 | 从任务卡能定位执行、版本、修改和审查证据，反向从工具回执能定位任务；重启后仍能查询 | 只有 Task 草稿或在对话里写计划 |
| **P3 Dispatcher 最小可执行流** | 接收已发布工作、能力路由、持久队列/领取、资源写入占用、并发协调、可靠状态迁移、错误与未知结果、审查交接、重启核对 | 真正派发单个任务并持续推进；冲突写入不静默执行；中断后只恢复安全未派发工作 | 模型说“已派工”、仅更改 Task 状态、Dispatcher 变成主 AI |
| **P4 岗位及多 Agent** | Persona / Duty / Agent 实例 / 模型 / 会话 / 权限分离；主 AI、施工、审查、验证及可兼任秘书职责；多 Agent 并发会话/工具调用 | 两个不同 Agent 在不重叠范围真实并发施工，可共享模型但权限/身份独立；职责变动不自动扩权 | 多个 Agent 名称、轮换单会话、角色等同系统管理员 |
| **P5 审查/验证/持续施工恢复** | 独立 Review/Verify、按证据退回同卡修复、主 AI 根据真实回执再次派工、待用户决定升级、停止/取消/崩溃/断网/撤权恢复 | R-01～R-08 满足，工具成功≠验证通过≠任务完成；未知副作用不可自动重试；正常重启保留有效状态 | 模型自述“已完成”、静态状态页、自动重放未知写入 |
| **P6 PC UI/安装与收口** | 最小项目、任务、Agent、对话、设置、执行/回执界面一体化；用户可选安装/数据/环境目录；重装凭证/授权失效；Windows 打包和真实使用流程 | 统一交付 SHA 的 Windows 安装、启动、真实工具、恢复和两种代码项目验收报告 | 源码启动代替安装验收；历史测试代替当前 SHA |

**并行施工规则**：批次表示验收依赖，不是瀑布式冻结。P1 的工具执行从第一天就记录 P2 所需的任务/操作可选关联；P2/P3 的任务状态与调度接口可同步开发；P4 的身份与权限约束在 P3 派发接口定义时预留。禁止为了赶进度把 Host 中的直接路径写入绕过核心授权模型。

## 三、按当前缺口安排的优先工作包

### W1 — P1 安全修改与终端执行（最高优先）

1. 整理 `wex-local-resources` 的直接叶子操作：固定目录句柄、版本/内容核验、单文件和未来批量操作的提交边界。**禁止**仅把非原子的 `replace_leaf_locked` 原位覆盖当成正式安全修改，也不得公开绕过重新授权的 `prepare_replace_leaf` 结果令牌。
2. 实现可安全提交的修改（必要时采用临时文件/原子替换及失败恢复方案），Windows reparse/hardlink/卷身份和 Unix symlink/mount/hardlink 规则均保持；实际提交前再次核对有效权限、目标版本和资源占用。无法保证原子性时保留拒绝/UNKNOWN，不声称支持任意覆盖。
3. 从当前 `cargo_test`、`cargo_fmt_check` 特例提取通用执行契约：已授权项目工作目录、程序及参数、环境来源、启动/超时/取消、进程状态、退出码、stdout/stderr 摘要、产物与工具结果；按权限/策略限制，不建立任意 shell 默认全盘执行权。现有 Cargo 特例可留作适配实例，不得成为最终能力白名单。
4. 本地 Git 的状态、Diff、分支与提交/冲突处理和 GitHub 写入/回读连接同一操作生命周期，外部结果未知不重试。普通对话与任务模式共用适用工具入口。

**W1 交付检查**：同一个授权项目读→改 A/B 两个文件→运行项目命令→取得失败→继续修复→本地 Git 变更/提交→回读证据。权限撤销、版本冲突、错误/未知写入均有独立结果。

### W2 — P2 任务事实与真实操作互相引用

1. 任务卡保留目标、约束、验收、真实范围、分派与当前状态，任务的版本冲突必须在领域服务拒绝。
2. 增加稳定引用链：`project_id → task_id/revision → assigned_agent_id → agent_session_id → dispatch_id/attempt_id → operation_id → receipt/evidence_id → file version/commit → review/verify`。普通非任务工具操作允许 task_id 为空，但仍需会话/操作身份。
3. 显式区分模型建议、已审批、已派发、外部工具成功/失败/未知、待审查、待验证、完成；状态真相属于 Rust 领域服务。
4. 把当前只读任务草案 UI 接到实际发布/派发操作，历史更改和未决阻碍可恢复。

### W3 — P3 Dispatcher 最小可用子系统

1. 编排只做确定性路由/队列/派发/占用/状态/证据，不替主 AI 规划、不扩大授权。
2. 派发时检查任务版本、Agent/Duty、上下文/资源范围、连接/OS/工具权限和策略；有副作用操作在 Host 执行时再次校验。
3. 明确互斥写入资源键、占用生命周期、冲突拒绝或挂起、恢复时校验/重建占用；不同资源允许并发。
4. 任务取消、执行者丢失、超时、UNKNOWN 的补偿策略：先核验外部事实，必要时提示用户，不盲目自动重放写入。
5. 首先闭环一个真实 Agent，然后在同一任务/工具契约上打开双 Agent 并发，而不是写两套派发机制。

### W4 — P4 多岗位 / 多 Agent

1. 可配置基础 Persona；Duty 允许一个 Agent 兼任多个责任；Agent 实例与 Provider/Model、Session、Connection、权限分别记录，不锁死岗位列表。
2. 两个 Agent 在各自有效授权范围并行，任务派发/结果回收按稳定 ID 关联；同一模型不意味着共享身份或授权。
3. 审查者默认不写代码；兼任岗位的 Agent 需保留每次操作时采用的职责/授权与实际执行身份。
4. 多 Agent 不能以并行对话代替施工，也不能用单工作树同时写同一路径冒充并发安全。

### W5 — P5 审查验证 / 主 AI 持续循环

1. Reviewer 读取同版本代码/Diff/要求和证据，生成引用具体 Task/Version 的审查结论。
2. Verifier 使用真实工具/证据标明环境、命令、结果和核对范围；模型评价永不直接冒充独立验证通过。
3. 审查退回后在原任务有效范围继续修复，再验证；新权限、新业务决策或无法消除的冲突升级到用户。
4. 恢复时确认已派发操作的外部状态，保留 UNKNOWN、取消与暂停状态；**自动继续**只适用于范围/权限/结果均已核实的待执行工作。

### W6 — P6 Windows 交付

- 连通首次启动、多个 API/模型、独立 GitHub/目录/终端授权、项目与成员设置、任务执行、回执/审查/恢复。
- 用户安装目录与资料/环境目录由用户选择；正常重启保留有效配置；**卸载重装或系统重装**不能因为历史资料仍在就自动恢复 Key/Token 和目录/工具有效授权。
- 待有 Windows 环境后分别以 WEXPC 和 Android 真实代码项目验收，记录安装包、提交 SHA、环境及失败证据。

## 四、跨批次必守的工程接口规则

- **授权独立**：项目、Space、Task、Agent 职责和模型相同均不自动授予 OS/本地文件/GitHub/终端权限。用户可配置自动、询问、拦截；在已授权范围内可连续操作，不退化为每次逐项确认。
- **任务与普通对话分离**：普通对话可以无需任务卡执行已授权工具；进入软件开发工作模式时才关联任务与持续派工。
- **写入冲突**：同一资源不能由两个 Agent 静默同时写；旧文件版本、目录绑定身份、任务范围、批准意图和结果证据必须在最终执行边界一致。
- **持久证据**：外部请求接受、已派发、结果已知/UNKNOWN、结果落盘和独立 Verify 分开；成功工具回执不意味着任务完成。
- **可扩展语义**：Connector、Dispatcher、Agent、工具协议和上下文不写死 DeepSeek/Cargo/Windows 单个演示模式；Windows 首版后续适配跨平台，不提前引入未经研究确认的新插件/策略体系。
- **架构边界**：Rust 领域服务维护权威状态；Tauri Host 控制凭证与本机实际能力；React 只管理交互/展示，不自建第二套任务或授权真相。
- **版本纪律**：不擅自将功能后移或更改 WEXPC 产品版本 0.1.1。功能接通、测试通过、Windows 验收分级报告。
