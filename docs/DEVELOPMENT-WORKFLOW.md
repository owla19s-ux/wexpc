### 两边的日常操作

大肥鱼先提交一次环境验通结果（不是安装计划）：

```sh
uname -sm
cargo --version
rustc --version
rustc -vV
git rev-parse HEAD
```

再运行一个能实际编译、执行并断言结果的Rust测试，以及本机回环HTTP测试，确认编译器、运行库、socket和必要C/TLS依赖。若失败，记录精确命令和脱敏错误；能转到Work本地验证的先转交，不转去触发Actions。

`wex-api`起点交接、依赖和锁文件就绪后，大肥鱼的模块验证命令才是：

```sh
cargo fmt -p wex-api -- --check
cargo test -p wex-api --locked
cargo clippy -p wex-api --all-targets --locked -- -D warnings
```

当前crate不存在时不要求运行这些命令，也不能把缺少crate当作手机工具链失败。新增依赖由双方先核对手机目标兼容性；确需试验时可在隔离副本验证，把依赖清单交Work统一更新共享配置/锁文件，避免两边争改根锁文件。

Work当前已确认工具在 `/root/.cargo/bin`，但默认PATH未包含它；可使用绝对路径，或在当前Work shell先执行下列设置。手机必须使用其实际安装位置，不照抄Work路径；“PATH找不到”不能直接认定工具未安装。

```sh
export PATH="/root/.cargo/bin:$PATH"
```

Work按实际改动先跑相关包/测试，批次集成时再运行必要的整体检查：

```sh
cargo test --workspace --locked
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo fmt --all -- --check
cargo fmt --manifest-path apps/desktop/src-tauri/Cargo.toml -- --check
```

前端在 `apps/desktop` 目录执行 `npm ci`（依赖变化或环境缺失时）与 `npm run build`。命令成功只证明对应检查；Rust平台条件编译未执行的Windows用例、缺失桌面依赖时未执行的Host编译，必须单列NOT_RUN。手机测试通过后由Work做受影响集成验证，不要求双方机械地重复全部测试。

### 编号、时间、身份和追加规则

- 每条记录的正式编号为 `REC-<GitHub评论ID>`，评论锚点即 `issuecomment-<ID>`；平台ID用于唯一引用，不要求连续，不能由双方各自从001抢号。初始记录为 `REC-6386453733`。
- 展示顺序以平台 `created_at` 为登记时间，统一显示北京时间/`+08:00`，同时间用评论ID作稳定排序。初始记录登记时间为 `2026-10-25T00:09:29+08:00`（平台原值 `2026-10-24T16:09:29Z`）。序号不是代码版本，也不是执行先后或依赖证明。
- 实际开始/结束时间另写，格式 `YYYY-MM-DDTHH:mm:ss+08:00`；不记得就写“未单独计时”，不能把补录时刻伪造成测试发生时间。离线补录同时保留实际执行时间和平台登记时间。
- 创建评论前生成唯一事件去重键，例如UUID，放入正文；网络超时/结果未知时先按此键读取日志确认是否已发布，不盲目重发。正式编号由平台返回，无需为了填编号编辑正文；后续记录使用评论链接和REC编号引用。
- 执行者明确写 `GPT Work` 或 `大肥鱼`；如共用GitHub账号，平台作者不能替代这个声明，也不能冒写对方已执行或已接收。
- 正常纠错追加 `CORRECTION` 并指向旧记录，说明哪些结论被替代；不悄悄编辑历史成果/测试结论。意外出现凭证或私人信息时先移除敏感内容，再登记脱敏更正，不重复公开原值。
- 本文仍维护最新能力表；环境变化必须同时追加ENV记录并引用证据。环境可测、测试已跑、测试通过是三种状态，不能互相推导。

```text
已完成：实际修改，不把计划写成成果
实际验证：环境/目标平台、命令、结果、退出码、日志或摘要
未验证：NOT_RUN项目、原因、后续所需环境/命令
下一步／接收者：
争议或待用户裁决：无则明确写“无已收到分歧”
```

记录中引用的源码SHA必须已存在；代码先提交再追加VERIFY/HANDOFF，START记录则引用已存在起点。计划中的分支、函数、crate不填为已完成。跨环境无法访问的临时日志路径注明“临时/未持久”，另附可回读的摘要或证据，不假定另一端能打开自己的本地文件。

### 双方同步与范围受理

1. 开工前读正式规范、本文能力/分工、有效契约、共同日志（包含续页和引用记录）及目标分支HEAD，确认没有待决条目影响本任务；不能只读自己上一条记录或旧摘要。
2. 申请范围时追加CLAIM；既定文件所有者/协调者Work串行登记受理，说明范围、起点、契约和受理哪条领取记录。大肥鱼收到明确交接/受理后才改所持模块，不能自行确认自己的领取。Work在自己的既定范围内开工也应登记START。
3. 受理后复读日志，核对没有同范围新分派。不同分支仍须避免同文件同时施工；新增共享依赖或接口变更先CHANGE，等待所有者处理。范围交还、改派、暂停和重新接手都追加记录。
4. 本日志是工程协作约定，不是数据库锁、租约或WEX产品内Dispatcher。若同时出现两条重叠CLAIM，两方先不修改重叠处，由Work登记唯一受理；若Work也有争议，登记待用户裁决。不能把“已经写了领取评论”当作程序化互斥。
5. 交付后接收者读取真实源码/Diff和证据，追加ACCEPT/NEEDS_FIX/BLOCKED；ACCEPT须区分“资料已接收”“本地集成通过”和“平台/真实服务验收通过”。未收到对方记录前保持“待对方确认”，不由Work代签大肥鱼。
6. 提交前、收到交接后、准备开始下一批前再读日志。两端是独立会话，无常驻监听或自动消息互通；按工作节点主动同步，不要求用户转述技术结果，也不假装对方已自动获知。
7. 离线或暂不能写日志时本地暂存含去重键的记录，不能宣称已经同步，也不抢领新的共享范围。恢复后先读最新日志和HEAD，再去重追加并核对是否仍能继续。

### 分歧与用户裁决

双方在范围、契约、实现选择或验收上出现不同意见时，共同日志追加DECISION_PENDING。待决编号沿用该评论REC编号，不另抢连续号；不得把尚未收到的另一方意见写成事实。

```text
事项及受影响任务/文件/契约版本：
当前依据：具体规范、代码或证据链接
GPT Work观点及理由：
大肥鱼观点及理由：未收到则明写待回复
可选方案：各自影响、返工/环境/验证代价
各自建议：建议不是裁决
需要用户明确决定的问题：
暂停的依赖工作：
可继续的无争议独立工作：
状态：DECISION_PENDING_USER
```

裁决前不修改依赖该争议的接口或范围，不把容易实现的方案先做成事实；无关独立工作可继续。双方已同意且属于既定需求内的常规实现细节，可按既定所有权推进，但不能把双方技术共识冒充用户新增需求或扩大权限。

用户明确决定后，由记录者追加DECISION_RESOLVED：引用待决REC、用户决定的原意/可用来源（没有消息链接就写会话日期和明确指令，不编造URL）、适用范围、对应契约版本及受影响任务。未收到用户决定就保持待决；AI建议、投票或单方总结不能替代裁决。需要双方改接口时再分别追加采用/接收记录。

## 每批开工

先读[一屏状态](../COLLAB/STATE.md)，再读共同日志新增及本任务契约；不要求每个小批重复通读全部长文档。状态文件由Work串行整合，双方历史仍在共同日志，不迁移到尚未定义同步方式的双分支JSONL。


1. 先读[项目共识说明](PROJECT-CONSENSUS.md)，首次接手或范围变更时各自在共同日志回执理解/疑问，不代签双方已一致。核对用户最新明确要求、PC 基线相应章节与原 WEX 文档的适用范围；标明已确认、讨论/候选、已实现、已验证和废弃。冲突指出具体位置，不能选择容易实现的一版。
2. 查 WEXPC 最新 main、开放 PR/分支、目标源码和相关 Actions。确认当前 HEAD 与工作分支、已有独有成果和真实差距；不得按旧交接总结重复施工。旧 WEX 只读追溯，不把改动提交到旧仓库。
3. 说明本批依据、实际差距、交付后用户可操作行为和验收方式。常规实现细节可自主决定；范围、权限、UI、模块选型与阶段目标不得暗改。长任务可分批，但保留完整目标和剩余项。
4. 代码变更核查实际依赖、配置、调用路径、权限、结果及 UI 接线；下载源码、声明依赖、模拟响应、单文件测试都不等于真实集成或完整能力。

## GitHub 分支、PR 和 Actions

- 在 WEXPC 使用有明确范围的分支和 PR；继续已有 PR 时先核对 head/base 和最新提交。不要强推 main；合并/清理分支前核对独有提交、审查状态和最终测试 SHA。
- 文档规范直接修订权威正文及冲突入口，不增添多份互相矛盾的“补充版”。PR 的文档修改不等于代码实现。
- 查 Actions 从仓库运行列表、Job 和失败日志开始，不反复向用户索取 Run ID。区分未触发、排队、取消、环境失败、编译失败、测试失败。
- 批次内相关提交集中验证；暂停期内所有源码/文档提交都跳过Actions，当前开发分支只保留手动入口且本期不使用。暂停期结束后再按实际影响评估触发规则，不沿用旧自动检查频率。需要安装包或实机体验时才做相应构建。
- 不提交密钥、私人数据或未审查的构建产物。凭证不能进入模型上下文、日志、PR 文本或普通数据库。
- 报告 PR/Commit、改动路径与验证证据；自动化结果必须对应实际交付 SHA。分别列代码、自动化、真实 API/GitHub、Windows 构建和 Windows 实机状态；未运行明确标注。
