# WEXPC 项目共识说明：我们在做什么、首版做到哪里

日期：2026-10-25。适用：GPT Work、大肥鱼及后续接手者。

**状态：依据现行需求编写的共同阅读说明，等待双方各自阅读回执；不是双方已签收证明，也不新增需求。** 正式范围以[PC产品与技术基线](PC-PRODUCT-AND-TECH-BASELINE.md)为准；本文负责用直白解释和例子建立相同理解，不维护另一份独立功能清单。基线变化时同步修订解释，发现冲突登记共同日志，不能自行采用容易实现的版本。

## 1. WEX 是什么，为什么现在先做 PC

WEX 的方向是把连接、工具调用、调度、交互与可接续工作组织起来。普通AI对话是入口之一；项目目标、任务、操作状态和真实证据需要独立保存。软件开发是第一个重点工作模式，长期还要容纳小说等其他工作。

现在的主线是WEXPC，首期Windows。PC具备较完整的文件、进程、Git和代码环境，适合实现持续开发；用户预计在11月下旬或12月上旬购买电脑，希望届时已有可继续开发的基础版本。这是安排优先级的背景，不是承诺届时完整0.1.1一定验收完成。

我们希望用户最终能说：“继续WEX项目，先处理上次没通过的测试”，软件能够找到正式目标、未完成任务、实际修改和测试结果，继续在已授权范围内工作。用户不应每次重新解释项目，也不应靠翻聊天猜测是否真的提交过代码。

## 2. WEXPC 与 Android 的关系

| 问题 | 共同理解 |
| --- | --- |
| 是不是两个无关产品？ | 属于WEX同一产品方向；代码仓库分开，运行平台、UI和交付证据分别管理，不假定数据或代码会自动同步 |
| 当前先做哪个？ | PC优先；Android不作为当前首要施工主线，但保留其成果与需求来源，不等于永久放弃Android |
| Android有什么价值？ | 参考连接、安全/撤权、操作生命周期、回执、失败恢复、API协议规则和相关测试；平台无关Rust可定向复用 |
| 哪些不能直接照搬？ | 手机导航、Flutter工程形态、Android系统接口、旧阶段删减、对象限制和验收结果不能直接成为PC规则 |
| 是否审完旧代码再做PC？ | 否。按当前用例快速判断：可直接复用则接入，需适配则明确边界，不为全量旧代码审查长期停工 |
| APS和DSH的关系？ | APS提供辅助设计参考；DSH提供本地Agent链路与可选外部执行者的参考。未据此选定其运行时、权限默认值或安装依赖 |

Android 0.1.1的原目标包括普通对话、API与工具、GitHub、本地多目录文件操作、角色、轻项目等日常使用链路；其产品内自动多AI施工曾是后续工作。**PC 0.1.1已经明确包含主AI分派、多Agent并发、独立验证审查与接续开发，不能继承Android的阶段后置。** 两端版本号相同，不表示范围相同；两端原基线均不能被说成已整体冻结或已完工。

具体来源：Android对照为WEX PR #72提交 `aa9044584977e9833be27e5f00c25fe37b528642` 的产品矩阵，PC对照为本仓基线§2、§5、§6。Android矩阵06.01曾规定轻项目不另建Project根对象；该约束不覆盖PC现行Project/Context关联实现。Android把AI浏览器后置，也不等于PC永久取消此方向；PC浏览器首批深度仍不能擅自承诺。

例子：Android上的“主对话＋左右抽屉”可帮助理解用户如何组织工作，但不能据此把Windows也做成放大的手机页面。Android的Dart API控制器可提供流终态/工具参数反例，依赖Flutter与安全存储的部分不能原样装进Rust/Tauri。

## 3. 0.1.1 的明确结果：用 WEXPC 继续开发 WEX

首版要求用户在Windows安装并打开WEXPC，配置AI/API与模型，选择真实项目及相应授权，组织目标和任务，让多个可区分的Agent实际读写代码、调用本地或外置工具链运行/测试/编译，根据反馈继续修复，使用本地Git/GitHub，并保存进度供重启后接续。在已确认目标、授权与执行策略内可以连续操作，不把每个文件或命令变成逐项重新授权；新范围/新权限仍须处理。普通工具对话不强制先创建任务卡；软件开发模式负责更持续的组织、分派与交接。

| 首版不可丢的能力 | 用户应得到的效果 | 不足以称为完成的情况 |
| --- | --- | --- |
| 基础Space/可选Group/Context与轻项目 | 保存目标、背景、资源引用、任务、分工和阻碍；能管理不同真实项目 | 只有聊天列表或临时演示数据 |
| API/模型与成员绑定 | 独立配置连接/模型、调用和工具协议；不同成员有可区分身份及会话 | 只有依赖声明、一个非流式文本请求或几个人名 |
| 本地Agent工作链 | 在授权范围连续读写多处代码、运行命令、读取退出码/日志再继续 | AI说“改好了”，但无真实执行和结果 |
| 主AI与多Agent施工 | 主AI梳理/分派，独立任务可并发；系统范围占用/执行隔离阻止重叠写入并检查集成冲突 | 单Agent换名字；仅口头约定不要改同一处 |
| 验证、审查与修复交接 | 对应版本的独立审查、实际测试/构建证据和同范围修复；无法判定时升级 | 施工者自述通过就自动完成任务 |
| Git与GitHub | 实际状态/Diff/提交/回读；失败和结果未知如实保留 | 模拟SHA、建议补丁或请求接受即宣布成功 |
| Android开发环境 | 选择/调用可用SDK与模拟器，安装运行、测试并取日志 | 编译APK、模拟器和真机三者混算一个通过 |
| 恢复与接续 | 退出页面、重启或中断后保留目标、进展、已发生操作与剩余工作 | 自动重发结果未知的写操作或要求用户重讲项目 |

界面应有可达、可操作、有反馈的入口，当前基础页面不冻结为最终UI。自由画布、多视图接线不作为首版门槛；多项目保存/切换仍需要，跨多个项目同时自治调度可后续深化。模型组合、并发上限等实施细节不能从测试样例倒推成产品限制。

### 例子A：两名施工者并行，另有验证和审查

用户提出“完善API流式回复，同时补任务接续”。主AI先核对目标和现状，形成目标、范围、负责人、验收明确的任务。API施工者改协议模块，另一施工者改任务服务，独立部分可并发；若双方都要改同一公共类型，系统应阻止同时写入，并处理依赖和集成，而非让AI口头保证。验证者实际运行测试，审查者针对对应Diff与规范检查，问题进入修复交接。没跑Windows时仍标Windows未验证，不能被手机测试或审查文字抵消。

这是**0.1.1目标场景，不是当前已经跑通的演示**；例子中的文件范围与成员数量用于说明，不是固定限制。

### 例子B：用PC继续开发Android

用户在Windows选择WEX Android代码项目及授权目录，Agent读取错误、修改多个文件，调用已有Flutter/Android SDK构建，在选择的模拟器安装运行并读取日志。若SDK缺失就报告缺少环境；若构建失败就保留错误并继续同范围修复。模拟器通过后仍由用户分别进行手机真机体验。WEXPC不必自行打包整套语言SDK，但必须完成环境发现/选择、实际调用与结果接线。

### 例子C：跨天继续

昨天代码已提交，但Windows测试未做；今天打开项目，应看到对应Commit、已有手机/Work测试、Windows待验证项及下一步。一次生成中断不应清空任务，也不能推断已派发的写操作没有发生。恢复的对象是正式工作状态，而不只是上一段聊天文字。

## 4. 分批施工与后续版本

当前先做架构/Core基础、Space/Context与轻项目，是施工优先级；A基础、B本地Agent、C多Agent/Git、D集成验收是同一0.1.1内的建议批次，不是另外四个产品版本。先交可用基础，不取消尚未完成的首版要求。

下表是对基线§5.3的解释，**0.1.2～0.1.5归属仍为建议/候选，不是已批准排期或承诺**：

| 版本 | 方向与例子 | 确认边界 |
| --- | --- | --- |
| 0.1.1 | 在选定的真实项目里组织多Agent、实际施工与验证、重启后继续开发 | 首版目标已确认，完整实现/验收未完成 |
| 0.1.2建议 | 完善工作组织与交互；例如同一任务从列表切到画布仍是同一对象 | 画布可后置已确认，必须在哪一版交付尚未确定；基础语音深度也待确认 |
| 0.1.3建议 | 协作深化；例如跨项目协调和更复杂的多轮交接 | 不能把0.1.1已经要求的基本多Agent、验证审查推迟到此版 |
| 0.1.4建议 | 跨环境/设备；例如按授权用手机查看和遥控PC、接收用户配置的通知 | 手机查看与执行权限分开，配对不自动扩权；具体连接器分项确认 |
| 0.1.5候选聚合 | 更多工作模式与生态；例如小说资料/章节组织、知识库、角色表现、账号/可选云服务 | 属长期方向候选，具体功能与版本归属待确认，不承诺发布日期 |

## 5. 长期方向如何影响今天的设计

- **工作对象通用。** Space → 可选Group → Context用于组织工作，不把全部Context固定成代码仓库。例：小说构思Context可以没有项目、GitHub或施工成员；软件项目可关联Context。
- **对象与视图分离。** 今天列表里的任务以后可以出现在画布或看板，不应为了换视图重建业务身份。它不要求现在提前交付完整画布。
- **连接与权限分离。** 一个Context可以引用本地、GitHub和服务资料；引用地址不会自动授权。例：关联`D:\\资料`不等于AI可以读里面所有文件，系统文件权限也不等于AI授权。
- **工具与组织分离。** 普通对话可按适用权限使用工具；不强迫用户每次读文件都启动软件开发任务体系。
- **秘书与多工作模式保留。** 长期可跨Context汇报进度、处理待决事项，按设置在全屏场景静默或通知手机；小说等领域不必采用软件开发专属任务结构。秘书、语音、角色/TTS、公共知识库与账号/云服务的具体深度和版本分别确认，不能一并塞入首版。
- **外部Agent可选。** 用户可在买电脑后用独立DSH继续开发；这不依赖WEXPC先完成DSH接入。以后若接入，WEXPC仍保有正式状态、授权、范围隔离和证据责任，目前未确定为必装依赖。

## 6. 当前事实，与我们今天的施工分开看

截至本说明起点 `072861024b5d05b82a7f89e212594cd4e005eb73`：

| 类别 | 当前事实 |
| --- | --- |
| 架构与基础 | Tauri/React → Rust应用服务 → SQLite正式路径已建立；Core Catalog已有实际复用，基础组织/项目和独立成员会话已接线 |
| 轻项目 | 任务草案可建/改/分配成员；可追加手动进展/阻碍/交接并保留旧任务快照；主AI工作资料包含本项目团队和全部任务 |
| 证据边界 | 手动记录和引用未自动核验；“分配草案”不等于程序已派工，“主AI资料完整”不等于主AI能自动发布/执行任务 |
| 未接通 | 完整API/工具循环、真实本地工具、Dispatcher施工/范围占用、独立验证审查修复链、Git/GitHub与模拟器桌面集成仍缺 |
| API交接 | 独立`wex-api`、可编码契约和模块起点尚未建立；契约为DRAFT-0；未代签大肥鱼接收或手机工具链验通 |
| 既有验证 | 业务源码`91cafba`已有248项本地Rust测试、前端构建及对应Linux/Windows CI证据；不替代后续源码、真实服务、Windows交互/凭证库、安装包或模拟器验收 |

今天GPT Work与大肥鱼通过不同分支、共同日志和本地环境协作，是**工程D域**；WEXPC未来在产品里自动分配、占用范围、执行和审查，是**产品M域**。例：今天在PR评论领取任务只是工程约定，不能当作软件内已实现范围锁。手机/Work本地优先及10月31日前暂停Actions同样是临时工程安排，不是WEXPC永久不支持云端验证。细则见[工程操作](DEVELOPMENT-WORKFLOW.md)。
