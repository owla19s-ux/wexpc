# WEXPC Context / 角色 / 能力与权限组合边界审计（2026-10-27）

状态：**架构审计与未决事项**，非审批通过的具体接口；本批仅文档，不改代码、不变更 0.1.1 交付范围。顶层权威语义以 main 的 `docs/PC-PRODUCT-AND-TECH-BASELINE.md` 第 0 节为准。

## 1. 本轮审计范围与事实

检查了 main 的：产品基线、0.1.1 施工计划、desktop-service 的 domain/mod.rs、domain/organization.rs、application/mod.rs、application/execution_policy.rs 与 core/dispatch.rs；未运行 Rust、Host、UI、Windows 测试。

已观察到的实现：
- `Context { id, name, goal, resources: Vec<String> }`，目前资源是引用性字符串；`ContextPlacement` 单个主要展示位置，移动不授予权限。
- `Project.resources` 同样是引用；Context 与 Project 的关系不能当作底层 OS/连接器授权。
- Agent 仍有旧 `project_id`、`role` 等字段；`assign_agent_duty(agent_id, project_id: Option<String>, duty_id)` 支持多项分配，但结构主要以项目为范围，不等同任意 Context/跨范围职责。
- `ToolPolicySetting` 用 `conversation_id + capability_id + policy + revision` 标识，不能独立证明“Agent 使用哪个岗位、在哪个 Context、针对哪个资源获得权限”。
- `core/dispatch.rs` 对任务派工检查 project、agent、assignment epoch；注明 Host 仍须验证实际授权和资源占用；这不是完整跨 Agent/Context 授权链。
- 现有 application 系统提示明确声明：岗位、资源地址和项目资料本身不赋予访问权。这是正确边界，禁止在新设计中倒退。

## 2. 发现及严重程度

### F1 — 上下文资源表达能力不足（高，扩展缺口而非漏洞）
`Vec<String>` 只能表达非常薄的地址引用，难以区分本地/云端、资料、连接、工具、其他 Context 或 Agent，以及引用目标的稳定身份、实际可用状态和引用用途。**不能直接得出应在 Context 上存放完整 ACL 或工具清单**；更不能因关联自动启用工具。

### F2 — 独立角色与跨 Context 工作语义尚未落地（高，模型不匹配）
多职责登记已经存在，但现有可选 `project_id` 不足以表达同一 Agent 的外部独立入口、参与多个 Context、跨项目研究协作和不同工作关系。旧 Agent.project_id/role 不应被误当长期不变量。无需现在确定职责/关系的具体数据表。

### F3 — 工作环境身份未贯穿执行检查（高，接线缺口）
Conversation+Capability 的工具策略与 Core Task+Agent 的 DispatchTicket 各自有用，但缺少当前工作入口、岗位作用范围、目标资源和真实 Host 授权的统一可核对关联。应避免两个相反错误：一个入口的岗位权限在另一个入口自动继承；或者为所有对话强制创建 Task。

### F4 — 自带工具 vs WEX 工具 vs 外部 Agent（中，能力边界不完整）
模型宣称拥有搜索/编程能力、API 实际开放工具调用、WEX 提供的执行工具、外部 Agent 的封闭式运行环境不是同一种能力。WEX 对其内部执行、数据传输、回执的可控性不同。工具来源不自动授予目标资源权限；委托 Agent 也不等于直接借用它的工具。能力目录/授权算法暂不冻结。

### F5 — 数据交付与模型侧留存（中，未来安全约束）
操作读取授权不自动等于向任意外部模型/API 发送内容的授权。禁止承诺入口切换即彻底清除已发送给第三方或保留在模型上下文的数据。未来本地模型和数据/策略支柱属于长期方向，不因该审计纳入 0.1.1。

## 3. 用三个最小场景审视新语义

1. **Context 内研究 AI 自带搜索**：允许其在确有能力且有效授权时搜索；不推断 WEX 可审计其内部搜索全过程，不推断可修改受研究的项目。Context 可以引用多个项目的资料而不拥有项目。
2. **Context 内施工 AI 使用 WEX 本地工具**：角色在该 Context 的授权仅为相关工作范围；Host 对具体路径/操作再次检查；使用已有工具和回执，不复制另一套权限引擎。
3. **外部独立决策 AI 请求修改某项目**：项目内曾担任负责人的身份不能沿用到外部直接操作；需独立有效的目标项目授权。向项目负责人提出建议与实际修改是不同动作。

这三种都能在顶层概念上由既有体系组合表达，**尚未通过端到端运行验证**。

## 4. 推荐的审计次序（非新版本排期）

- **第一步：术语与归属检查**。将“Context 位置 / 项目业务 / Agent 身份 / 工作职责 / 关联资源 / 真实授权 / 能力来源”在接口审查中分开，检查旧项目字段被硬编码为统一父容器的地方。
- **第二步：最小端到端运行验证**。用已有资源引用与 Host 权限检查，验证外部角色入口不能直接越权改项目、Context 内 AI 的授权有效、普通对话无需 Task。优先复用现有代码并补契约测试，而不是预建全部资源类型和 ACL。
- **第三步：待讨论设计**。Context 所能关联的资源/连接实例/工具/角色是“可发现/可引用”还是“可使用/可执行”？其用途、授权与撤销如何表达？这是用户明确暂缓的问题，禁止本提案替其拍板。
- **第四步：模型与外部 Agent 能力差异**。围绕三类场景验证工具来源及 WEX 的实际控制/回执边界，作为架构扩展审查，不提升现行 0.1.1 的版本要求。

## 5. 审计结论

**没有发现需要推翻三大产品支柱、现有 Core/Dispatcher/Host 职责或重新建设统一工具引擎的证据。** 主要风险是“旧项目中心字段和会话中心工具策略不足以表达已确认的独立角色+多 Context 语义”，而不是现有授权安全机制本身已经失效。Context 的工具与资源关联仍处于开放讨论阶段；在此之前仅确认“引用 ≠ 授权，能力 ≠ 执行许可，项目内权限 ≠ 外部入口授权”。
