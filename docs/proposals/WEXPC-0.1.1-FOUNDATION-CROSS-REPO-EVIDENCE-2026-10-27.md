# WEXPC 0.1.1 前期范围：WEX 与 WEXPC 双仓文档核对（2026-10-27）

**状态：证据核对/研究结论；未替换 main 施工计划，未改代码或触发 CI。** 用户要求不再重复询问现有文档已足够回答的问题，直接以 WEX 原始设计和 WEXPC 当前基线确定前期基础。前中后均属于 **0.1.1 内部分期**，不是单独产品版本。

## 1. 已有设计明确支持，无须重新设计顶层

- `WEX/docs/WEX-DESIGN-BASELINE-2026-10-17.md` §1.1：Space 用户组织、可选 Group；Context 不等于 Project；可按需关联 Address/Resource/Connection/Conversation/State/Task 等而不强制齐全。软件开发结构是可选 Context 能力。多个地址和 Connection 可组合，地址≠授权。
- `WEX/docs/PRODUCT-SPEC.md`：P 通用产品能力、M 产品内可选开发模式、D 开发 WEX 的工程活动需分开；不把 M 设为 P 的必经入口。
- `WEX/docs/baselines/WEX-0.1.1-PRODUCT-FEATURE-MATRIX.md`：01.01~01.04 普通对话及会话模型/工具选择；02.01~02.05 API 与工具循环；05.01~05.03 角色卡独立管理；06.04/06.06 多地址及默认选择；07.01~07.03 搜索/Fetch 跨模型；03/04 含 GitHub 和本地文件。**为需求追溯，不继承旧 Android 版本交付裁决。**
- `WEX/docs/architecture/PLATFORM-TOOL-ACCESS-LAYER.md`：Connection 与 Tool 不同，一个连接可提供多个 Tool，多个连接亦可提供同类 Tool；能力发现、授权、执行、回执分开。完整 PTAL 插件运行时不是前期必建物。
- `WEXPC/docs/PC-PRODUCT-AND-TECH-BASELINE.md` §0.1~0.4：三个产品能力领域、Context 能力自由选择、角色独立、模板非本体；§2.2/§2.3 普通会话和连接器；§6.2 追溯原 WEX 范围。
- `WEXPC/docs/PROJECT-CONSENSUS.md` §5：组织工作对象通用，小说 Context 可不含项目、GitHub、施工成员；连接与权限分离。
- `WEXPC/docs/WEXPC-0.1.1-IMPLEMENTATION-PLAN.md`：当前 P1~P6 以开发工具闭环、任务、Dispatcher、多 Agent、审查、Windows 交付组织，**是工程路径并非通用 Context 的领域结构**，与新确认的“前期先通用基础”排序须重映射，不直接废弃既有工作包。

## 2. 前期应能独立交付的用户路径

1. 无模型、无模板时，用户可创建 Space、可选 Group、Context，保存名称、目标和 0..N 资源位置与引用；移动分类不转移资源所有权或授权。
2. 用户配置一个或多个 AI API/Provider/Model，普通 Conversation 可以不属于 Context、Project、Task 或 Agent；选择模型，发送/流式接收、保留历史、错误与取消状态。
3. 用户独立创建/管理角色卡与 Agent，按当前会话或 Context 选择职责，不依赖固定项目成员关系；角色提示不产生工具访问权。
4. 用户可见实际连接实例及它提供的各项能力，按 Context/会话选择具体工具或连接；一个连接的多项能力可选用部分，选中≠授权。
5. 一个极简 Context 可只有一个资源地址 + 一个 Agent + 搜索/Fetch（若搜索连接实际配置可用）；获得有效授权后可查询并将来源与工具结果返回对话；无 Task/Project/软件开发模板。
6. 在适用授权内，普通对话能经通用工具循环调用已提供的文件/GitHub 等工具；不要求软件开发工作模式作为执行前置。操作记录区分成功/失败/未知，真实副作用可回读核对。

**前期最低验收矩阵（均需实际验证）：** 离线组织、独立对话、多连接模型选择、Agent 无项目创建、单 Context 可选组合、连接禁用及授权撤销、工具循环、状态持久恢复、原软件开发 Project/Task 旧数据兼容。

## 3. 中后期边界先不冻结

- **中期**：在通用组合上组织软件开发这一工作模式，轻项目/Task/岗位默认组合，并研究简单模板是否有必要进入本期；完整模板编辑器、继承/版本迁移系统不自动成为 0.1.1 要求。
- **后期**：真实 Dispatcher 派发、多 Agent 并发、文件/终端/Git/GitHub、Review/Verify、可持续修复、Windows 安装与实际测试验收；这些功能仍属于 0.1.1 既有目标，不因内部分期而删减。
- 注意：权限、操作生命周期、可追溯回执的**通用契约前期就要存在**，不能把基础执行边界拖到后期。

## 4. 审计根因与后续改造顺序

旧 Agent `project_id`、固定 role、自动项目会话、成员判断与简报按固定项目产生，是将**软件开发模式默认绑定**提升为通用 Context/Agent 规则的实例。不能大规模删除现成代码：先识别通用对象、关系、能力目录和用户可选项，再在兼容迁移中缩小旧字段的职责。删除 Context 关联不等于撤销系统实际授权，更不等于删除外部资源；反之，取消授权必须阻止后续不合规工具执行。

## 5. 与现行文件冲突待改项

- 当前实施计划 P1 “本地开发工具闭环最高优先”不再适合作为**整体前期的唯一主线**；需要补一个通用基础先行的依赖视图，保留安全开发工具工作包但重新排先后。
- PC 产品共识目前以“利用 WEXPC 开发 WEX”为首版主要叙事，应增补“先形成可独立使用的通用 Agent 客户端与 Context 能力组合”，不能用产品内开发模式代表通用核心。
- 现行 Context 结构只含 id/name/goal/resources，Agent 创建依赖 project_id；这两处是兼容改造/增量模型的直接审计入口。
- 不应据此恢复旧 Android 0.1 的 M 后置规则覆盖 WEXPC 0.1.1 的已确认多 Agent 施工目标；区分平台与日期优先级。
